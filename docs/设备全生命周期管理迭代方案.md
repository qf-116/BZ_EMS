# 设备全生命周期管理迭代方案（简化流程修订版）

> 版本：V1.3（简化流程修订版）
> 修订日期：2026-09-18
> 适用对象：设备管理系统标准版前端演示及后续生产实施规划

> **当前开发口径**
> 以 [设备全生命周期管理功能设计方案-V1.2-当前版](./设备全生命周期管理功能设计方案-V1.2-当前版.md) 为当前功能依据，V1.1 作为字段级详细参考。上一版中到货、安装、调试、技术验收的独立页面不再建设；统一收敛为“采购入账 → 使用部门试用确认 → 设备办理手续入账”一个流程任务。附件红线范围同步执行：变更不做移位，闲置不做保全，报废不做处置执行。

## 1. 结论先行

当前标准版已经覆盖“设备启用后的运行管理”：设备台账、联网监测、报警、点检/巡检/保养、维修、备件、OEE 和报表。缺口集中在“设备形成前”和“设备退出后”，以及资产状态变更的审批和留痕。

本次迭代建议新增一个独立的 **设备全生命周期管理域**，通过业务单据驱动设备状态，不建议只在设备台账中直接编辑生命周期状态。

目标闭环：

```text
采购入账（设备名称、型号、数量、品牌、发货时间、合同等）
      → 使用部门试用确认
          ├─ 合格 → 设备办理手续入账（上传验收单和档案、补全台账）
          └─ 不合格 → 退回采购
      → 运行维护（现有模块）
      → 调拨/改造/借用/外送
      → 闲置/复核/再启用
      → 报废/鉴定/财务核销/归档
```

产品边界建议：SRM/采购系统负责物料、供应商、采购订单和合同等采购事实；设备管理系统只承接采购入账后的流程任务、使用部门试用确认、设备手续入账、资产变更、闲置和报废归档；固定资产资本化、折旧和财务核销仍由 ERP/财务系统负责。

### 1.1 交付定位与版本边界

本方案同时描述“当前标准版原型”和“未来生产系统蓝图”，两者必须分开立项、排期和验收，不能把原型演示能力视为生产上线能力。

| 层级/系统 | 本方案内职责 | 明确不承诺 |
|---|---|---|
| 标准版前端原型 | 生命周期页面、演示数据、模拟审批、模拟外部单号、状态机和跨页联动剧本 | 真实鉴权、真实电子审批、附件存储、ERP/财务对账、生产数据迁移 |
| 生产版设备生命周期模块 | 流程任务、试用确认、设备手续入账、资产变更、闲置、报废归档、附件、消息、幂等、并发控制和审计证据 | 采购付款、会计凭证、固定资产折旧、处置执行等完整外部系统能力 |
| 宿主平台 | 身份、组织、角色、数据权限、统一待办和平台操作审计 | 设备生命周期业务规则和设备状态事实 |
| SRM/采购系统 | 物料主数据、物料分类、供应商、采购订单、合同和采购事实 | 使用部门试用确认、设备手续入账和设备运行履历 |
| ERP/OA/财务系统 | 预算、资本化、折旧、核销等权威数据 | 试用确认、设备手续入账、闲置复核和设备运行履历 |
| 点检/保养/巡检承接模块 | 计划、任务、执行结果和复机/保全任务落库 | 生命周期申请、审批和资产状态维护 |

当前标准版仍是前端演示系统。迭代 1 如未同步建设后端，应明确采用“模拟审批 + 模拟接口 + 演示状态机”口径；生产实施的工期必须另行评估。

### 1.2 对 SRM/WMS + 设备管理双来源模式的判断

该模式总体合理，推荐采用，但必须把“来源分层”和“业务责任”分开：

1. **SRM 管采购事实**：物料、供应商、采购订单和订单行由 SRM 维护，设备管理系统只保存引用和必要快照。
2. **WMS 管仓库事实**：经过仓库的设备，以 WMS 的实际收货、库位和交接为主要来源；WMS 不覆盖的直送现场场景，可由 SRM 收货或设备管理系统手工登记承接。
3. **设备管理系统管设备业务事实**：从“设备类收货记录”开始确认设备实例、现场交付、安装、调试、验收、建档和启用，不重复做仓储收货。
4. **双来源必须进入同一状态机**：同步和手工只是 `sourceType` 不同，不能形成两套到货表、两套审批和两套后续流程。
5. **手工新增是受控兜底，不是替代接口**：直送现场、临时收货或接口故障可以手工登记，但必须待核验、可追溯、可对账，并设置补录期限。
6. **必须防重复和可更正**：同一实际收货不能同时被 WMS/SRM 和人工生成两条有效记录；退货、冲销、数量更正采用反向事件或版本更正，不物理删除原始记录。

因此，推荐的主流程是：

```text
SRM/采购系统或人工提供采购入账信息
                      ↓
             使用部门试用确认
                ↙             ↘
             不合格           合格
              ↓                ↓
          退回采购      设备办理手续入账
                              ↓
                       设备台账/运行管理
```

该边界比在设备管理系统内建设完整采购、到货、安装和调试模块更合理，能够避免采购和设备资产数据重复维护；主要实施风险集中在试用确认责任、入账资料完整性、台账编码唯一性和财务核销衔接。

## 2. 现有系统基线与缺口

### 2.1 已有能力

- 设备资产：设备台账、设备详情、综合文档库、基础类型配置。
- 现场运营：点检、保养、巡检、维修、备件。
- 运行数字化：联网配置、实时监控、报警、OEE、停机事实、程序比对。
- 管理分析：运行、生产、维修、报警、备件、点巡保养等报表。
- 状态层已经使用 DemoStore、reducer、domain 和 selector 组织业务闭环，适合继续扩展生命周期状态机。

### 2.2 关键缺口

1. **缺少 SRM 收货同步和设备物料识别**：没有定义哪些物料属于设备、收货记录如何进入本系统、如何处理重复/部分/冲销收货。
2. **缺少到货/入厂后的设备业务**：无法基于 SRM 收货记录记录设备实例、开箱检查、资料齐套、缺陷和退货影响。
3. **缺少安装调试过程**：没有现场条件确认、安装计划、调试项目、试运行数据、问题整改和厂家服务记录。
4. **缺少正式验收**：无法区分技术验收、安全验收、性能验收、资料验收和最终验收，也没有“条件通过/整改后复验”。
5. **缺少资产启用机制**：采购日期、启用日期目前是台账字段，不能由验收通过自动形成资产并触发二维码、责任人、位置、保修和监测配置。
6. **缺少资产变更履历**：调拨、移位、换责任人、改造、扩展、拆分/合并、借用/外送等变化无法审批和追溯。
7. **缺少闲置/停用闭环**：没有闲置原因、保管措施、定期复核、再启用条件和闲置资产盘活过程。
8. **缺少报废/处置闭环**：没有报废技术鉴定、残值、环保/安全处理、拆除、处置去向、财务核销和最终归档。
9. **缺少统一生命周期履历**：现有设备详情应增加从采购到处置的时间线，而不是把信息分散在多个列表页面。
10. **缺少流程级约束**：当前台账编辑是演示交互，状态可以直接修改；正式开发后必须改为“动作 + 前置校验 + 审批 + 状态变更 + 审计”。

## 3. 目标业务架构

### 3.1 建议菜单

建议收敛为以下业务入口，避免在“设备资产”下平铺过多菜单；采购申请和采购执行不在本系统实现：

1. 生命周期工作台
2. 到货与验收（SRM 收货同步、到货确认、安装、调试、验收）
3. 资产变更（调拨、移位、责任人、改造、借用/外送）
4. 闲置与处置（闲置、复机、报废、处置、归档）
5. 设备台账
6. 文档中心
7. 生命周期分析

各业务入口内部再设置列表、详情、发起、执行、审批待办和异常处理视图。现有“设备台账”和“综合文档库”保留，并在设备详情中增加“生命周期履历、采购信息、验收资料、变更记录、闲置/报废记录”等 Tab。

### 3.2 角色建议

| 角色 | 主要职责 |
|---|---|
| 使用部门 | 提供设备使用场景和安装位置，参与试运行和使用验收 |
| 设备管理员 | 编码、资产建档、安装调试组织、验收组织、状态维护 |
| SRM/采购人员（外部角色） | 供应商、采购订单、收货更正和到货异常协同 |
| 仓储/门卫 | 到货登记、入厂、暂存、开箱和数量核对 |
| 厂家/服务商 | 安装、调试、培训、整改、保修服务 |
| 安全/质量人员 | 安全、特种设备、质量和合规验收 |
| 财务人员 | 资产价值、资本化日期、折旧/核销接口确认 |
| 部门负责人/分管领导 | 采购、变更、闲置、报废审批 |
| 系统管理员 | 流程模板、编号规则、主数据和接口配置 |

权限、组织和平台操作审计继续复用宿主平台能力；本模块只定义业务单据、审批条件、候选角色、状态迁移和业务证据。正式实施前必须形成“单据 - 动作 - 角色 - 审批规则 - 数据范围”RACI 矩阵，并满足申请、鉴定、验收、财务确认和最终处置之间的职责分离。

### 3.3 最小审批责任矩阵

| 单据/动作 | 发起 | 必审/确认 | 执行 | 关键职责分离 |
|---|---|---|---|---|
| SRM/WMS 收货同步异常 | SRM/WMS/集成服务 | 采购、设备管理、质量 | 接口运维/采购 | 原始收货事实以来源系统为准，本系统不改写同步记录 |
| 到货确认/异常 | 仓储/设备管理员 | 采购、质量、使用部门 | 设备管理员或供应商 | 检查人和差异关闭人应分离 |
| 安装调试 | 设备管理员 | 使用部门、安全/质量（按设备类型） | 厂家/工程人员 | 执行人与最终验收人应分离 |
| 设备验收 | 设备管理员 | 使用、设备、质量/安全、财务确认方 | 整改责任方 | 厂家不能代替甲方验收签署 |
| 调拨/闲置/复机 | 设备或使用部门 | 原属部门、接收部门、设备管理 | 设备管理员 | 原责任人与接收责任人双确认 |
| 报废/处置 | 使用或设备部门 | 技术鉴定、财务、资产负责人、分管领导 | 处置执行人 | 鉴定人、审批人、处置确认人分离 |

## 4. 核心流程与状态机

### 4.1 设备收货到启用

```text
设备类物料主数据 → SRM/WMS 收货或设备系统手工新增
→ 待核验 → 到货确认/设备实例识别 → 安装中 → 调试中 → 待验收
→ 整改中 → 复验
→ 验收通过 → 已建档 → 已启用
```

异常分支：接口失败、物料待分类、手工记录待核验、部分收货、收货冲销/退货、到货不合格、调试失败、验收不通过、条件通过待整改。

### 4.2 运行中的资产状态变化

```text
在用 → 调拨中 → 在用
在用 → 变更审批 → 在用
在用 → 闲置申请 → 闲置
闲置 → 再启用申请 → 调试/点检 → 在用
在用/闲置/停用 → 报废申请 → 鉴定 → 待处置 → 已处置 → 已归档
```

### 4.3 状态字典与事实来源

建议拆成四个状态轴，避免与现有实时状态和维修状态混淆：

- `assetStage`：待核验、待收货确认、待安装、调试中、待验收、已建档、已处置、已归档。
- `useStatus`：未启用、试运行、在用、闲置、停用、报废申请、已报废。
- `operationStatus`：运行、待机、计划停机、故障停机、维修中、无数据，沿用现有监测域，不使用“离线”替代通信健康。
- `custodyStatus`：在途、在厂待检、暂存、正常保管、借用、外送、处置中。

现有 `lifecycleStatus` 仅作为过渡展示字段，由新状态轴派生，禁止与新字段同时作为可写事实源。正式实施时必须提供版本化迁移适配器，不得因状态结构升级而静默清空历史快照。

### 4.4 状态迁移和联动矩阵

| 业务状态 | 实时监测/报警 | OEE | 维修 | 点巡保养 | 联网绑定 |
|---|---|---|---|---|---|
| 未启用/待验收 | 可用于调试验证，不进入正式报警 | 不统计 | 记录调试问题，不建正式维修工单 | 不进入正式计划 | 可配置但不得标记生产生效 |
| 试运行 | 按试运行策略监测并单独标识 | 默认不计正式 OEE | 可建试运行问题单 | 可生成试运行检查 | 保持启用并标记试运行 |
| 在用 | 正常参与 | 满足绑定和速度配置时参与 | 正常 | 正常 | 正常 |
| 闲置 | 暂停生产报警，保留必要环境/保全监测 | 不统计 | 允许保全性维修 | 切换为保全计划 | 默认保留绑定，不等同解绑 |
| 停用 | 暂停生产报警，历史可查 | 不统计 | 按停用原因决定 | 暂停或生成专项任务 | 保留配置，必要时停用采集 |
| 报废申请/处置中 | 停止生产报警，保留处置安全监测需求 | 不统计 | 阻止新增普通维修 | 停止常规计划 | 处置完成前受控停用，不直接删除历史绑定 |
| 已归档 | 只读历史 | 不统计 | 只读历史 | 只读历史 | 解绑或停用，保留版本历史 |

所有实时、报警、OEE、维修和任务页面必须通过统一的 `selectLifecycleEligibility` 或等价领域服务判断准入，禁止页面直接读取 `lifecycleStatus` 自行判断。

### 4.5 关键门槛定义

- **建档**：设备实例已经形成，可生成资产卡片，但不代表技术验收、财务资本化或正式启用。
- **验收通过**：技术、性能、安全、资料等必选验收项通过；可触发建档或更新资产卡片。
- **条件通过**：只能进入受限试运行，是否允许生产、资本化和质保起算必须由项目制度单独配置，默认不等同正式启用。
- **资本化**：以财务系统回传或人工确认的权威单号和日期为准，不由技术验收单自行推导。
- **正式启用**：验收门槛、位置、责任人、必备资料和必要的联网/安全条件满足后，由受控动作完成。
- **归档**：处置凭证、财务核销回执、关联业务清理和历史保留均完成后才能进入。

## 5. 新增功能需求

### 5.1 SRM/WMS 收货来源与设备物料分类

- SRM 负责物料主数据、供应商、采购订单、订单行和采购收货；WMS 可作为实际仓库收货记录的来源。
- 设备管理系统不实现采购申请、比价、下单、付款和完整收货账，只接收或登记“设备类物料的收货记录”。
- 物料主数据必须有明确的 `materialCategory` 或 `assetizationFlag`，至少区分设备、备件、耗材、工装、组件和服务；只有设备类物料进入设备生命周期流程。
- 设备类物料还应配置设备类型、是否序列号管理、是否成套设备、是否需要安装调试、是否需要技术验收、默认验收模板和质保规则。
- 到货记录来源支持两条通道：
  - **系统同步**：SRM/WMS 通过 API、消息或批量接口传入；以外部收货单号 + 收货行号作为幂等键。
  - **人工新增**：设备管理员在设备管理系统手动新增，适用于直送现场、临时收货、WMS 未覆盖或接口暂不可用的场景。
- 手工新增记录必须标记 `sourceType=MANUAL`，填写来源说明、采购单号/供应商/物料编码（如有）、收货凭证和创建人；默认状态为“待核验”，不能伪装成已同步的 SRM/WMS 收货。
- 原则上手工记录仍应关联 SRM 采购订单/订单行；确属直送现场、紧急采购或历史补录而无外部单号的，必须填写例外原因、责任人和补录期限，并在建档/验收前完成复核。
- 人工记录可先启动后续到货确认，但在正式建档或验收前应完成外部单号补录、采购/仓储复核或人工放行，并记录对账结果。

### 5.2 设备到货/入厂管理

- 到货记录统一模型：来源系统、外部收货单号、收货行号、采购订单/订单行、物料编码、设备类标识、供应商、收货数量、单位、收货时间、收货地点、批次/箱号、序列号和附件。
- 收货来源不是业务分支：同步记录和手工记录进入同一状态机、同一详情页、同一设备实例识别流程；差异通过来源、核验和对账状态体现。
- 到货处理状态：待核验、已确认、待检、合格放行、不合格隔离、退货影响、已关闭；原始 SRM/WMS 收货事实只读保留。
- 开箱检查：外观、铭牌、数量、随机附件、说明书、合格证、校准证书、备件和工具。
- 暂存隔离：未放行设备不得进入安装现场；不合格设备需记录隔离区域、整改/退货责任方和关闭证据。
- 设备管理系统的“到货确认”不是再次记一笔仓库收货，而是确认设备实例、资料和现场交付条件，避免与 WMS 重复记账。
- 支持一条收货记录对应多台设备、多批次、部分收货、序列号后补和成套设备拆分；收货冲销、退货或数量更正必须由来源系统回传或由人工对账处理。
- 收货设备在正式验收前不得进入“在用”或正式 OEE；可进入受控安装/调试状态。

### 5.3 安装与调试

- 安装条件确认：基础、供电、气源、水路、网络、安全防护、环境和吊装条件。
- 安装任务：计划、负责人、厂家、开始/结束时间、现场照片、施工记录。
- 调试方案：空载、负载、精度、节拍、联机、报警、安全联锁、能耗等项目。
- 安全与合规：高风险施工许可、能源隔离、吊装/动火、特种设备证书、计量器具校准、试运行安全确认。
- 试运行记录：试运行时长、产量、良率、关键参数、异常、停机和整改措施。
- 问题闭环：问题登记、责任方、计划完成日、整改证据、复验结果。
- 培训交接：操作、维修、安全培训和培训签到。

### 5.4 设备验收

- 验收申请：由设备管理员发起，自动带出 SRM 订单引用、收货、调试和物料技术规格资料。
- 验收清单：技术、性能、质量、安全、环保、资料、备件、培训、外观和资产信息。
- 结果：通过、条件通过、整改后复验、不通过、退货。
- 条件通过：默认只允许受限试运行；允许生产、资本化、质保起算和正式启用分别配置门槛，不得用一个“条件通过”同时代表全部放行。
- 签署与留痕：验收人、使用部门、设备部、质量/安全、厂家、验收时间和意见。
- 验收通过动作：生成/激活设备资产、确认启用日期、启动质保、生成二维码、绑定位置/责任人、可选触发联网配置和点巡保养计划。
- 验收不通过动作：资产不得启用；保留问题、整改和复验记录。

### 5.5 资产建档与启用

- 自动生成设备编码、资产编号或接收外部系统编码。
- 完善基本档案：序列号、制造号、品牌型号、原值、安装日期、启用日期、质保起止、供应商、合同/采购单、位置、责任人。
- 打印二维码/铭牌，二维码进入设备详情和履历。
- 关联综合文档、说明书、图纸、验收单、培训记录和保修条款。
- 启用校验：必须验收通过、位置和责任人已确认、必备资料齐套；需要监测的设备还要完成 IoT 绑定。

### 5.6 设备变更管理

- 调拨：部门、车间、产线、工位、责任人变更。
- 移位：位置变更及对产线/OEE/联网配置的影响评估。
- 资产属性变更：分类、名称、型号、重要等级、OEE 资格、技术参数。
- 技术改造：改造内容、改造前后参数、费用、供应商、重新调试/验收。
- 拆分/合并：主设备、子设备、组件和父子关系。
- 外送/借用/返厂：出厂、归还、责任人、预计归还时间和保管状态。
- 生效与纠正：每次变更记录计划生效时间、实际生效时间、影响范围和纠正单；错误变更使用反向业务单纠正，不覆盖历史。
- 规则：在维修中、报废审批中、处置中的设备，不允许直接调拨或删除；变更前后必须保留快照。

### 5.7 闲置/停用与再启用

- 闲置申请：原因、开始时间、预计闲置时长、当前价值、保管地点、封存措施、盘活建议。
- 审批校验：未完成维修/验收/借用/报废流程的设备不得进入闲置。
- 闲置保全：定期通电、润滑、防锈、环境检查、点检任务和照片。
- 闲置复核：按月/季度提醒责任人复核，继续闲置、再利用、调拨、出租或报废。
- 再启用：状态恢复前完成解封、点检、试运行、联网检查和责任人确认。
- 状态区别：闲置表示设备可用但暂不投入生产；停用表示因故障、技改、安全隔离或管理决定禁止使用，两者采用不同审批、保全和再启用门槛。

### 5.8 报废与处置

- 报废申请：技术寿命、故障频发、维修经济性、产线淘汰、安全/环保、闲置超期等原因。
- 技术鉴定：设备现状、维修价值、预计残值、可拆部件、危险物质、照片和鉴定意见。
- 多级审批：设备部、使用部门、财务、资产负责人、分管领导；金额或特种设备按规则加签。
- 处置方案：报废拆除、内部调剂、出售、回收、返厂、以旧换新、环保处理。
- 处置执行：拆除日期、承包商、称重/交接、去向、残值收入、环境和安全证明。
- 处置证据：处置方资质、拆除/称重记录、资产交接单、回收收入凭证、危险废物或环保联单、现场照片必须按设备类型配置必传规则。
- 财务对账：保存核销申请单号、回执状态、失败原因、重试记录和人工确认人；“已处置”不等同“已归档”。
- 关闭条件：未关闭的维修/借用/联网绑定/库存关联必须处理；完成财务核销后才进入“已归档”。
- 禁止物理删除：报废设备及其履历只允许归档，所有业务资料长期可追溯。

### 5.9 生命周期总览、履历和报表

- 生命周期总览：按阶段显示待办、超期、金额、数量、异常和即将到期事项。
- 设备 360 履历：采购、到货、安装、调试、验收、启用、维修、保养、变更、闲置、报废、处置时间线。
- 管理指标：订单到货周期（基于 SRM 时间戳）、到货准时率、收货到启用周期、验收一次通过率、调试周期、质保期内故障率、闲置率、闲置时长、报废周期、处置回收率、生命周期成本。
- 预警：到货延期、调试超期、验收超期、质保到期、闲置复核到期、报废审批超期、资料缺失。
- 指标口径在迭代 0 固化：订单到货周期起点/终点（基于 SRM 时间戳）、收货到启用周期、验收一次通过率分母、闲置率按数量还是原值、处置回收率和生命周期成本的费用范围均需形成字段级公式。

## 6. 数据模型建议

### 6.1 业务对象关系

SRM/WMS 收货记录和设备资产不是一对一关系，正式建模必须采用明细层级；人工新增到货记录也必须落入同一模型：

```text
SRM 物料主数据 material_master（WMS 引用）
  └─ SRM/WMS 采购订单行 purchase_order_line（外部引用）
      └─ 收货记录 receipt_record（SRM/WMS 同步，或设备系统手工新增）
          └─ 收货明细 receipt_item（数量、批次、箱号、来源状态）
              └─ 设备计划单元 equipment_unit（单台/成套设备）
                  └─ 设备实例 equipment_instance（序列号/制造号）
                      └─ 资产卡片 device_asset（设备编码/资产编号）
```

- 一个采购订单行可分批形成多个收货明细。
- 一条收货明细可由 WMS/SRM 同步，也可先由设备管理员手工登记，后续再完成外部对账。
- 一个到货明细可形成多个带序列号的设备实例。
- 成套设备通过 `asset_relations` 建立主机、附机、组件关系，并保存生效区间。
- 验收、建档、启用均作用于明确的设备计划单元或设备实例，不直接对整张采购单或整张收货单“一键通过”。

### 6.2 新增业务实体

| 实体 | 关键内容 |
|---|---|
| `material_mappings` | 物料分类、设备类型、序列号/成套规则、验收模板和质保规则 |
| `purchase_order_refs` / `purchase_order_lines` | SRM 采购单引用、订单行和数量快照，不维护采购执行 |
| `receipt_records` / `receipt_items` | SRM/WMS 同步或人工新增的收货记录、来源、核验、数量和状态 |
| `equipment_units` | 收货后形成的单台或成套设备单元 |
| `equipment_instances` | 序列号、制造号、铭牌和实际设备实例 |
| `asset_allocations` / `asset_relations` | 实例到资产卡片分配、父子/组件关系及生效区间 |
| `installation_tasks` | 安装计划、现场条件、负责人、厂家和施工记录 |
| `commissioning_records` | 调试方案、试运行数据、问题整改和复验 |
| `acceptance_records` | 验收清单、结论、意见、签署人、附件 |
| `asset_change_records` | 调拨、移位、改造、借用、拆分/合并的前后快照 |
| `idle_applications` | 闲置原因、保全、复核、再启用 |
| `scrap_applications` | 报废原因、鉴定、审批、处置方案 |
| `disposal_records` | 拆除、交接、去向、残值、环保和财务核销 |
| `lifecycle_events` | 所有状态变更的统一事件时间线 |
| `workflow_instances` / `workflow_decisions` | 审批实例、节点、候选角色、决定、意见和超时信息 |
| `attachments` | 附件元数据、版本、哈希、签署信息和业务关联 |
| `external_refs` / `sync_tasks` | 外部主键、权威来源、同步状态、重试和对账错误 |
| `device_blockers` | 未关闭维修、借用、外送、绑定、库存等设备级阻断项 |

### 6.3 设备主数据建议新增字段

`assetStage`、`useStatus`、`custodyStatus`、`serialNo`、`manufacturerNo`、`supplierId`、`purchaseOrderNo`、`contractNo`、`arrivalDate`、`installationDate`、`commissioningDate`、`acceptanceDate`、`warrantyStart`、`warrantyEnd`、`originalValue`、`residualValue`、`currentLocation`、`assetSource`、`lifecycleVersion`。

现有 `buyDate`、`enableDate`、`lifecycleStatus` 保留兼容，但逐步改为由生命周期单据计算或同步，不允许用户在台账中任意覆盖事实。

### 6.4 外部接口和人工兜底

| 外部对象 | 权威来源 | 同步方向 | 失败兜底 |
|---|---|---|---|
| 组织、人员、角色 | 宿主平台 | 平台 → 本系统 | 保留上次成功快照，禁止自由文本替代审批人 |
| 物料主数据、设备物料分类 | SRM | SRM → 本系统为主 | 物料分类缺失时进入“待分类”队列，不允许按名称猜测设备类别 |
| 采购订单、订单行、供应商 | SRM | SRM → 本系统快照 | 仅保存外部引用和快照，不在本系统新建或修改采购订单 |
| 收货记录 | WMS/SRM | WMS/SRM → 本系统；设备系统可人工新增 | 同步失败进入重试/对账；人工新增标记 `MANUAL`，后续补录外部单号并复核 |
| 资产编号、资本化、核销 | 财务/资产系统 | 双向确认 | 记录失败原因、重试任务和人工确认，不因接口失败丢失业务单 |
| 点检/保养/巡检任务 | 承接业务模块 | 生命周期事件 → 承接模块，结果回传 | 原型阶段仅提示/模拟；生产阶段失败进入补偿队列 |
| IoT 绑定 | IoT 平台/现有数据接入域 | 生命周期命令 → 绑定域 | 暂停监测与解绑分开处理，失败时保持原配置并生成待办 |

收货同步最小字段：`sourceSystem`、`sourceReceiptId`、`sourceReceiptLineId`、`purchaseOrderId`、`purchaseOrderLineId`、`materialCode`、`materialCategory`、`assetizationFlag`、`materialName`、`model`、`brand`、`supplierId`、`receivedQty`、`unit`、`receiptTime`、`warehouse/site`、`batchNo`、`serialNo`、`sourceVersion` 和附件引用。序列号暂缺时允许后补，但必须在设备实例识别或验收前补齐/确认。

每个外部引用必须保存 `sourceSystem`、`externalType`、`externalId`、`syncStatus`、`lastSyncAt`、`errorCode` 和 `reconcileStatus`。同步接口使用服务端幂等键和唯一约束：同步收货建议以 `(sourceSystem, sourceReceiptId, sourceReceiptLineId, sourceVersion)` 控制重复和更正；手工新增建议以 `manualReceiptId` 作为本地唯一键，并要求后续与外部收货单对账。

收货更正规则：SRM/WMS 的退货、冲销、数量更正不能物理删除本系统记录，而是生成反向事件或更正版本；如果设备已经进入安装、调试或验收，系统必须转为异常处理，由设备管理员、采购/仓储责任人共同确认影响。

### 6.5 存量数据迁移

- 存量设备标记 `assetSource=存量建档`，允许仅有“历史简档”，不要求补齐全部旧采购、调试和验收单才能继续运行。
- 明确设备编码、资产编号、序列号、IoT 编码和父子关系的去重优先级及冲突处理人。
- 将旧 `lifecycleStatus` 映射到新状态轴，并对“报废/归档”合并值进行人工核验拆分。
- 迁移同时校验现有绑定、OEE 资格、开放维修工单、备件关联和点巡保计划。
- 提供预校验、正式导入、差异报告、回滚、导入审计和抽样验收；正式系统不得使用“不兼容即恢复初始状态”的策略。
- 原型快照升级应提供显式版本适配器，例如 `v4 → v5`，并保留迁移失败提示和可重置能力。

### 6.6 一致性与审计设计

- 验收启用、闲置、复机和报废使用聚合命令编排跨域动作，而不是由页面连续调用多个独立动作。
- 设备保存 `lifecycleVersion`，命令携带 `expectedVersion`，以乐观锁防止重复审批或并发覆盖。
- 外部副作用通过 outbox/补偿任务执行，可重放、可查询、可人工处理。
- `lifecycle_events` 采用追加写，记录 before/after、操作原因、单据、工作流节点、处理人、来源、关联命令和审计指针。
- 附件记录版本、哈希、签署人和签署时间；验收、报废等关键证据不得无痕覆盖。

## 7. 分期迭代方案

### 迭代 0：流程和技术基线（2~3 周）

目标是先把规则定死，避免页面先行导致返工。

- 冻结 `assetStage/useStatus/operationStatus/custodyStatus` 状态契约、迁移矩阵和联动矩阵。
- 定义物料主数据→采购订单行→收货明细→设备计划单元→设备实例→资产卡片的关系、编码和父子资产规则，并明确 SRM/WMS 同步和手工新增的统一模型。
- 确认 SRM/WMS/财务/ERP/OA/点巡保承接模块的系统边界、主键、同步方向和人工兜底。
- 固化设备类型技术规格模板、验收模板、附件证据规则、合规节点和通知规则。
- 设计 `lifecycle_events`、工作流、附件、外部单号、服务端幂等、乐观锁和补偿规则。
- 完成存量设备数据盘点、迁移映射、历史简档策略和抽样验收方案。
- 输出状态转移、非法转移、重复提交、并发、迁移、接口失败和跨域补偿测试用例。

交付物：流程蓝图、RACI 审批矩阵、业务对象关系图、状态/联动矩阵、字段字典、接口契约、迁移模板、测试用例和原型/生产边界说明。以上交付物未评审通过，不进入页面开发。

### 迭代 1：收货到启用原型 MVP（6~8 周，最高优先级）

覆盖新设备从收货到启用的单条主路径，优先解决“设备能不能按规则进入台账和运行系统”。若本期仍是前端演示，则使用模拟核验、模拟外部单号和模拟接口，不宣称生产可用。

- SRM/WMS 收货同步 + 手工新增到货记录（统一模型）
- 到货/入厂、来源核验、待检/隔离/放行和开箱检查
- 安装条件、安全确认和调试任务
- 验收清单、条件通过、整改、复验
- 建档、试运行和正式启用的门槛分离
- 设备生命周期工作台和设备详情履历
- 到货来源异常、接口失败、调试超期、验收超期提醒
- 必要异常：部分收货、到货不合格、手工记录待核验、重复同步、收货冲销/退货影响

一期不做采购申请、比价、下单、付款和财务折旧；SRM/WMS 负责采购和仓储收货，生产版同步接口须另行完成契约、重试和对账。

### 迭代 2：资产变更与闲置管理（4~6 周）

覆盖设备投产后的资产治理，防止台账和现场实际逐渐失真。

- 调拨、移位、责任人变更
- 技术改造及重新调试/验收
- 借用、外送、返厂和归还
- 闲置申请、审批、保全、定期复核
- 再启用检查和状态恢复
- 变更前后快照、设备位置和责任人历史
- 与维修、点检/保养、联网配置、OEE 的联动校验；当前标准版先实现提示和模拟事件，真实任务落库依赖承接模块接口

### 迭代 3：报废处置和资产退出（4~6 周）

覆盖设备从报废申请到归档，形成最后一公里闭环。

- 报废申请和技术鉴定
- 多级审批、金额/设备类型规则
- 处置方案、拆除、交接和去向
- 残值、回收收入、环保/安全附件
- 财务核销接口、回执对账和归档
- 报废设备受控停用/解绑、任务关闭和历史只读
- 闲置转报废、报废转内部调剂等分支

### 迭代 4：集成和运营优化（按项目资源安排）

- SRM/WMS/ERP/财务双向接口和幂等重试
- 移动端扫码、现场拍照、电子签名
- 供应商质量和质保索赔
- 生命周期成本和投资回报分析
- 资产盘点、二维码盘点差异和批量调整
- BI 主题分析和管理驾驶舱

## 9. 与现有系统的联动规则

1. **台账**：台账是资产主数据展示入口，新增和状态变更必须来自生命周期单据；禁止直接把“闲置/报废”作为普通编辑字段保存。
2. **监测**：只有 `useStatus=在用` 且已启用联网绑定的设备参与实时监测；闲置、停用、报废申请设备默认暂停监测和报警，保留历史数据。
3. **维修**：报废、调拨、闲置前检查是否存在维修中/待验收工单；未关闭时必须阻断或要求强制处理并留痕。
4. **点检/保养/巡检**：生产实施由生命周期事件/API 请求承接模块创建、暂停或关闭计划；当前标准版只展示联动提示、模拟事件或待办，不承诺真实任务落库。
5. **备件**：报废或改造前检查设备关联备件、拆下件和可复用件；生产实施通过库存接口完成处理，接口失败进入对账队列。
6. **OEE**：非在用设备不参与 OEE；停机、闲置和计划停机的口径要与现有 OEE 规则区分。
7. **文档库**：采购、安装、调试、验收、质保和处置附件统一关联设备和生命周期单据。
8. **工作台**：新增待审批、待到货、调试超期、待验收、闲置复核、报废审批、接口失败和人工对账等待办。
9. **跨域一致性**：验收启用、复机和报废使用聚合命令；页面不能串行调用多个动作并假设全部成功。每个副作用须有命令号、幂等键、状态和补偿记录。
10. **设备级阻断**：维修中/待验收、借用/外送、未完成联网变更、库存/备件关联、未关闭处置任务等统一进入 `device_blockers`，由生命周期动作集中校验，并使用版本号防止并发覆盖。

## 10. 每期验收标准

### 迭代 1

- 一台设备可以完成“SRM/WMS 收货同步或手工新增→来源核验→到货确认→安装→调试→验收→建档→启用”。
- 验收不通过时不能启用；整改后可复验，原意见和附件不丢失。
- 条件通过只能进入受限试运行；正式生产、资本化、质保起算和正式启用按配置门槛分别验证。
- 验收通过后能按设备计划单元生成设备实例/资产卡片、二维码、质保信息和责任人/位置信息。
- 单据状态、设备状态、工作台待办和设备履历保持一致。
- 部分收货、到货不合格、手工记录待核验、重复同步、收货冲销/退货和刷新重放结果符合预期。
- 每个页面只通过统一生命周期选择器判断是否进入监测、报警和 OEE，不允许自行复制状态条件。

### 迭代 2

- 一台在用设备可以完成调拨、移位、责任人变更和闲置/再启用。
- 变更前后信息可追溯，监测、OEE、维修和保养联动规则生效。
- 闲置设备按周期产生复核待办，复机前必须完成检查。
- 维修中、借用中、外送中或接口未完成时，闲置/调拨动作能够阻断并给出责任项。

### 迭代 3

- 一台设备可以完成报废申请、技术鉴定、多级审批、处置、核销和归档。
- 存在未关闭维修、借用、外送、联网绑定、库存关联或财务接口失败时，系统能阻断或进入明确的补偿/对账流程。
- 报废设备不能再出现在可用设备、OEE 和实时报警清单中，但历史履历和报表仍可查询。
- 只有处置证据、财务回执、关联事项清理和设备级版本提交全部完成后，才允许从“已处置”进入“已归档”。

### 10.4 跨域与生产化测试

- 状态转移矩阵：非法转移、驳回、撤回、退回、复验、条件通过、重新打开。
- 幂等与并发：重复点击、重复消息、跨标签提交、`expectedVersion` 冲突和重放。
- 副作用一致性：outbox 重试、部分失败、补偿完成、人工确认和最终履历一致。
- 迁移：`v4 → v5` 快照适配、旧状态映射、失败回滚、历史简档和现有绑定/OEE/工单兼容。
- 联动准入：闲置/报废设备不出现在实时、报警、OEE 和可用设备清单中；历史数据仍可查询。
- 外部接口：SRM/WMS/ERP/财务/点巡保任务重复、延迟、撤销、失败、死信和对账。
- 审批证据：节点、处理人、意见、附件版本/哈希、签署时间和 before/after 可追溯。

## 11. 开发前必须确认的 12 个问题

1. SRM 是否是物料主数据、供应商、采购订单和采购收货的权威系统？WMS 是否是仓库实际收货的权威系统？
2. SRM 与 WMS 是否都会产生收货记录，二者通过什么单号或接口关系去重和对账？
3. 哪些物料分类/属性代表设备，设备物料是否需要配置序列号、成套、安装调试和验收模板？
4. 到货记录是否全部由 WMS/SRM 传入，哪些场景允许设备系统手工新增？手工记录由谁复核、多久完成对账？
5. 一条收货记录是否会对应多台设备、成套设备和子设备？是否需要父子资产关系？
6. 序列号、制造号在 SRM/WMS 收货时是否必填，缺失时最迟在哪个节点补齐？
7. 验收是否需要技术、质量、安全、使用部门和财务分别签署？
8. “条件通过”是否允许先使用，还是必须整改完成后才能启用？
9. 固定资产原值、资本化日期、折旧和残值由哪个系统维护？
10. 闲置多久需要复核，闲置设备是否必须转移到专用保管位置？
11. 哪些设备属于特种设备，报废/迁移是否有额外合规节点？
12. 报废处置、宿主工作流、附件、电子签、审计、ERP/财务、点巡保养和 IoT 的接口责任方与失败兜底人是谁？

## 12. 对当前原型的落地建议

现有菜单曾在“设备资产”下预留采购申请、到货验收、安装调试、设备变更和报废处置入口；按新的系统边界，下一轮原型应按“生命周期工作台、到货与验收、资产变更、闲置与处置、生命周期分析”收敛信息架构。实现时建议新增：

- `src/domain/lifecycle.js`：状态契约、迁移矩阵、前置校验和 `selectLifecycleEligibility` 对应规则。
- `src/state/actions.js` / `reducer.js`：聚合命令、版本校验、申请、到货、调试、验收、变更、闲置、报废和处置动作。
- `src/state/selectors.js`：生命周期总览、待办、设备履历、设备级阻断和统一联动准入。
- `src/data/demo/lifecycle.js`：物料分类、收货、调试、验收、闲置、报废演示数据。
- `src/pages/*Lifecycle*`：按迭代 1~3 增加页面。
- `src/specs/pageSpecs.jsx`：同步新增页面的字段、状态和验收口径。
- `src/data/demo/migrations.js`：原型快照版本适配和存量状态映射样例。

第一批原型建议先做“生命周期工作台、到货与验收、到货/入厂、安装调试、设备验收、设备详情履历”六个页面，跑通一台设备从 SRM/WMS 收货同步或手工新增到启用的演示剧本，再扩展资产变更、闲置和报废。

### 12.1 评审结论

本方案经业务资产、产品实施和技术红队三视角评审后，结论为：**业务主线保留，开发前必须补齐边界、对象关系、状态矩阵、接口契约、迁移和一致性设计**。在这些准入项未确认前，不建议直接按原方案新增全部页面或承诺生产上线。

## 13. 2026-09-18 简化流程修订（当前执行版）

本节优先级高于本文档中此前关于“到货、安装、调试、技术验收、处置执行”的旧版描述。

### 13.1 当前主流程

```text
采购入账
→ 使用部门试用确认
   ├─ 合格 → 设备办理手续入账
   └─ 不合格 → 退回采购
```

采购入账字段只需覆盖设备名称、型号、数量、品牌、发货时间、合同、使用部门及必要附件；不在本系统建设采购执行。

使用部门只提交试用结论和意见：合格进入设备管理板块，不合格退回采购并保留退回原因和历史附件。

设备手续入账节点上传验收单和设备档案，补全设备台账信息，生成设备编码/资产卡片和生命周期履历；不再建设独立到货、安装、调试、技术验收展示。

### 13.2 当前保留范围

- 生命周期工作台和统一流程任务。
- 设备手续入账、设备台账和生命周期履历。
- 调拨、改造、借用、外送。
- 闲置申请、复核、再启用。
- 报废申请、技术鉴定、财务核销、归档。
- 生命周期分析。

### 13.3 当前明确不做

- 到货记录、到货核验、开箱检查。
- 安装管理、调试管理、试运行项目。
- 独立技术验收和条件通过复验。
- 变更中的移位。
- 闲置中的保全。
- 报废后的处置执行。

### 13.4 当前一期页面

1. 生命周期工作台。
2. 生命周期流程任务。
3. 采购入账任务。
4. 使用部门试用确认任务。
5. 设备手续入账任务。
6. 设备详情生命周期履历。

资产变更、闲置和报废页面按 13.2 的范围作为后续迭代，不扩展红线之外的功能。
