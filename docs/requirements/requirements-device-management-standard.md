## 一、结论摘要

### 1.1 总体判断

当前系统更准确的定位是：**功能覆盖较完整的标准版产品演示，已经形成设备资产、运行监测、报警、维修、备件、报表和 OEE 等主要业务域的产品框架；下一步重点不是继续增加菜单，而是把关键用户任务和跨模块流程做得更清晰、更完整、更易用。**

本次评审以“用户能否完成工作”为核心，而不是以演示数据是否完全对账或页面是否已经接入真实后端为核心。演示数据不一致本身不构成产品问题；只有当数据差异会让用户误解状态、找不到入口、无法完成操作或破坏业务规则时，才需要在产品层修正。

现有系统覆盖工作台、设备资产、维修、备件、数据接入、运行监测、报警、报表和 OEE 等主要业务领域；平台基础管理模块负责统一登录、身份、权限和平台日志，本系统不重复建设。IoT 平台负责连接和采集、设备管理系统负责业务设备与数据消费的边界方向总体合理，建议继续沿用。

当前最需要优化的不是“有没有页面”，而是以下用户闭环：

1. 设备管理员能否从设备档案顺利完成联网配置、指标选择、状态查看和影响范围判断；
- 生产/班组人员能否从总览或实时监控发现异常，理解异常影响，并依据宿主平台提供的业务动作上下文快速确认、处置或发起维修；
3. 维修人员能否接收到完整上下文，完成派工、维修、备件领用、验收和结果回写；
4. 管理人员能否从 OEE、运行、报警和维修报表看到同一设备的问题、原因、损失和改善结果；
5. 业务页面能否正确使用平台传入的用户与数据范围上下文，不在本系统重复建设公共管理能力。

### 1.2 最重要的产品建议

建议将标准版定义为：

> **围绕设备全生命周期和生产运行场景，把设备档案、联网监测、OEE、异常报警、维修协同、备件管理和经营分析串成一条用户可理解、可操作、可追踪的设备运营闭环。**

第一阶段不要以“页面数量”作为完成标准，而应以以下闭环是否可真实运行作为完成标准：

```text
设备主数据
  → IoT 绑定与指标选择
  → 数据健康 / 实时状态
  → 报警事件
  → 确认 / 处置 / 维修工单
  → 维修完成验收
  → 备件领用 / 退库 / 库存回写
  → 报表与设备履历
```

### 1.3 现有功能模块盘点：页面覆盖不等于能力交付

| 模块 | 当前产品覆盖 | 用户闭环状态 | 主要调整方向 |
|---|---|---|---|
| 工作台/总览 | 指标卡、异常设备、待办、近期记录 | 适合演示汇总，管理动作和下钻还不完整 | 明确服务对象、数据截止时间、异常优先级和处理入口 |
| 设备资产 | 台账、详情、编辑、附件、二维码、子设备入口 | 基础档案场景已覆盖，生命周期和跨模块履历需补齐 | 统一设备身份、状态轴、责任范围和历史履历 |
| 点检/保养/巡检 | 项目、标准、计划、任务、执行、报表页面 | 本次不展开内部设计 | 只保证异常转报警/维修/备件时复用公共对象 |
| 维修管理 | 故障报修、待维修、维修任务、执行、经验库、报表 | 页面链路存在，报修—派工—维修—验收跨页面闭环不足 | 明确负责人、SLA、停机、备件和验收回写 |
| 备品备件 | 备件台账、入库、出库、库存、报表 | 库存和单据场景已展示，领用、退库和工单关联需补齐 | 让仓库和维修人员看懂可用库存、预留、出库和退库 |
| 数据接入 | 联网配置、绑定总览、平台指标、程序比对、处理记录 | 接入运维入口已覆盖，异常处理和影响提示需补齐 | 让用户知道数据从哪里来、是否健康、异常影响什么 |
| 运行监测 | 总览、实时监控、设备详情、独立大屏 | 监控展示已覆盖，实时性、数据质量和入口职责需明确 | 区分运行状态与通信状态，统一异常下钻和大屏用途 |
| 报警中心 | 报警列表、确认、处置、关闭、批量动作 | 报警操作路径已展示，通知、转维修、恢复和关闭规则需闭环 | 统一状态、责任人、SLA、通知结果和维修关联 |
| 报警规则/通知 | 规则、模板、版本、通知策略 | 配置概念较完整，用户处置结果和通知结果不够可见 | 保留基础规则治理，补充发布影响、通知状态和升级路径 |
| 报表中心 | 运行、生产、质量、报警、维修、备件、综合等多页 | 报表种类较全，查询、下钻、导出和指标解释需增强 | 收敛用户主题，统一筛选、口径说明和下钻路径 |
| OEE | 实时、历史、详情、速度、计划停机 | 已属于标准版核心能力，重点是让结果可解释、可行动 | 完善目标、趋势、损失解释、常用筛选和停机/报警/维修/质量联动 |
| 系统公共服务 | 由平台提供，不在本系统重复建设 | 本系统消费平台提供的身份、组织和权限上下文 |

其中，“用户闭环状态”是本次评审结论，不是对页面是否存在的否定。后续 PRD、报价和验收单应把“已做页面”“可演示交互”“真实数据接入”“业务闭环可验收”分成四种标签。

## 二、整体判断与现有设计优点

### 2.1 IoT 与业务系统边界的方向是对的

《架构设计-数据接入与物联网平台集成V2.md》明确不在本系统重新维护 PLC、网关、协议、点位地址和转换规则，这是非常重要的边界优化。否则标准版会同时承担 IoT 平台和设备管理系统的职责，导致：

- 点位配置重复维护；
- 两个平台的指标定义不一致；
- 设备来源和业务设备无法区分；
- 采集故障责任无法判断；
- 后续新增设备类型的实施成本显著增加。

建议将该边界写入产品需求、对接约定、平台菜单可见性和验收协议，而不是只停留在架构文档中。

### 2.2 “一台业务设备关联 1 个主设备 + N 个子传感器”的模型合理

设备管理系统的一台业务设备关联 IoT 平台多台来源设备，是实际工业现场常见场景。按来源设备分组展示指标，也能解决多个传感器存在同名指标的问题。

但该模型必须补齐统一身份、版本、占用校验和换绑过程，见后文 P0 要求。

### 2.3 报警规则中考虑了防抖、回差、重复抑制和风暴保护

当前规则细则已经考虑：

- 候选状态与持续时间；
- 迟滞回差；
- 同一活动事件重复触发抑制；
- 风暴限流和事件合并；
- 规则发布版本快照；
- 通知策略与升级节点。

这些设计比简单的“超过阈值就弹窗”成熟很多，应保留。但需要把配置规则真正映射到事件引擎、通知记录和报表，而不是停留在页面说明。

### 2.4 数据质量不应被简单等同为在线/离线

设计中已经区分正常、延迟、离线、缺失、无效、补传、重复等质量状态，方向正确。尤其是“不把无数据当作 0”“离线设备不参与稼动率分母”等规则，能够避免报表产生严重误导。

问题不在于质量模型方向，而在于当前质量数据、缺失区间和补偿任务没有真实的查询、执行和结果闭环。

### 2.5 维修来源区分较清晰

维修任务区分报修登记、监测异常和快速维修，能够表达不同的业务来源和处理责任。该方向应继续保留，但必须统一报修、待维修、维修任务和维修履历的数据对象，不能让各页面各自持有一份数组。

## 三、必须先解决的范围与基线问题

### 3.1 明确“演示范围”和“标准版能力”的关系

当前 README 展示了 12 个一级模块，页面数量较多；这不代表所有页面都已经具备生产级闭环，也不代表 OEE 只是预留功能。应把产品说明拆成以下四种标签：

- **标准版核心能力**：设备资产、联网监测、OEE、报警、维修、备件和基础分析；
- **当前需要完善的能力**：跨模块状态回写、下钻、通知、停机和配置生效反馈；
- **演示或原型能力**：用于展示交互路径的静态数据、模拟操作和占位按钮；
- **后续扩展能力**：预测性维护、复杂算法、移动端以及未纳入合同的资产供应链功能。

PRD、报价和验收单应分别说明“页面可访问”“可演示交互”“真实数据接入”和“业务闭环可验收”，避免因为演示页面已出现，就让客户误以为每个动作都已生效；也避免因为历史文档未更新，就误以为 OEE 不属于当前标准版。

### 3.2 统一当前产品基线，历史材料只作背景参考

当前标准版的功能范围应以现有产品页面、交互设计、功能说明和已确认的用户目标为准。历史架构或旧版实施材料如果与当前标准版不一致，应标记为待更新或背景参考，不能用历史材料否定已经上线的 OEE 等当前能力。

建议在 PRD、报价和验收单中明确区分：

1. 当前标准版已经包含的功能；
2. 当前版本需要完善的功能；
3. 仅作为后续扩展的功能；
4. 本系统明确不负责的 IoT 底层采集、远程控制等能力。

对于 IoT 接入、MES 数据和 OEE 统计，仍需确认各方责任、数据来源、时间口径和异常处理规则，但这些确认的目的，是让已纳入标准版的功能可稳定使用和验收，而不是把 OEE 从标准版范围中排除。

### 3.3 把设备覆盖范围作为产品配置，不把演示数量当成系统事实

当前演示页面展示的设备数量和各模块样例数量不完全一致，这在演示阶段可以接受。本产品层需要明确的不是“页面上是否都显示 46 台”，而是每台设备在业务上的覆盖范围：哪些设备只纳入资产管理，哪些设备已联网，哪些设备参与运行监测、报警和 OEE，哪些设备具备生产或质量数据。

建议建立设备覆盖矩阵，至少能让实施和用户查看：

| 字段 | 要求 |
|---|---|
| 业务设备统一身份标识 | 系统内部永不复用 |
| 资产编号/设备编号 | 面向业务和现场标识 |
| IoT 主设备统一身份标识 | 与显示编码分离 |
| IoT 子设备/传感器列表 | 记录角色、来源和生效版本 |
| 可采指标 | 指标统一身份标识 + 版本 |
| 生产数据能力 | 有 / 无 / 待确认 |
| 程序比对能力 | 有 / 无 / 不适用 |
| OEE 资格 | 已确认 / 未确认 / 不纳入 |
| 责任部门、产线、工位 | 用于组织范围筛选和统计 |
| 接入验收状态 | 未接入 / 联调中 / 已验收 / 已停用 |

## 四、核心数据和主数据设计调整

### 4.1 建立统一设备身份，让用户能查看完整设备履历

当前演示数据中存在不同模块使用不同设备编码的情况，演示阶段可以接受；但生产产品必须让用户从台账、监测、OEE、报警、维修和报表进入同一台设备，而不能因为名称、序号或编码变化打开另一台设备。

建议产品上提供一个统一的设备身份，并允许同时展示业务设备编号、IoT 来源设备编号和现场名称。所有跨模块入口都应携带该设备身份，设备改名、换绑或停用后仍能查询历史报警、维修、OEE 和资产履历。

### 4.2 区分“配置状态”和“健康状态”

设备管理员和生产人员需要分辨：设备是否已配置、是否已联网、最近有没有数据、当前是否故障或停机。这些不是同一个状态。

建议至少区分：

- 配置状态：未配置、待生效、已启用、已停用、换绑中；
- 通信健康：正常、延迟、部分中断、数据中断、未知；
- 生产/运行状态：运行、待机、计划停机、故障停机、维修中、无数据。

停用设备不应简单显示成离线；未联网设备不应产生数据中断报警；只有部分传感器中断时，应显示部分中断并说明影响哪些指标。

### 4.3 设备删除规则要改为“归档/停用优先”

设备一旦产生监测、报警、维修或 OEE 履历，用户不能通过删除动作让历史消失。建议：

- 只有草稿且无引用的设备允许删除；
- 已启用或已产生业务记录的设备使用停用、闲置、报废、归档；
- 设备报废后历史数据、报警、维修和 OEE 履历仍可查询；
- 资产位置、责任部门、负责人和联网关系变更都形成履历，并在相关页面显示影响范围。

### 4.4 明确组织、班次、工厂时区和宿主平台数据范围上下文

用户需要知道自己负责哪些工厂、车间、产线和设备，也需要确保不同班次和跨天生产不会被统计到错误的日期。产品应明确：

- 单工厂还是多工厂，是否多租户；
- 车间、产线、班组和设备的组织层级；
- 设备是否可以跨组织由宿主平台的组织范围上下文决定；
- 班次日历、跨日班次和节假日如何维护；
- 统计时区和数据的统计截止时间；
- 来源时间、接收时间和数据延迟如何展示。

OEE、报警、运行和维修报表的筛选条件应保持一致，用户从一个页面下钻到另一个页面时不能丢失设备、时间、班次和组织范围。

### 4.5 设备详情应成为跨模块工作的统一入口

- 设备详情不应只展示静态档案。用户进入一台设备后，应能看到当前配置/联网状态、运行健康、OEE 摘要、活动报警、未完成维修、近期停机、备件使用和历史履历，并能依据宿主平台传入的业务动作上下文进入对应处理页面。

建议在详情页明确区分“当前状态”和“历史记录”，对无数据、未配置和已停用设备提供原因说明；从报警、维修、OEE 或报表返回设备详情时保留原有筛选条件。这样设备详情才能成为用户查找问题和判断责任的工作入口，而不是信息展示页。

## 五、物联网接入与数据消费设计

### 5.1 联网配置页应让用户完成“识别—验证—选择—生效—追踪”

当前 `DeviceNetConfigPage` 已有 IoT 主设备、子传感器和指标选择的配置方向，但用户还需要一条清晰的操作引导：输入或选择来源设备后，系统应验证它是否真实存在、当前是否已被占用、有哪些可用指标；保存前应展示将影响哪些监控、报警和 OEE；保存后应说明配置何时生效、当前状态是什么以及如何查看历史版本。

生产实现至少必须满足：

1. 输入编码后能够识别 IoT 平台中的来源设备，并展示统一身份标识、当前连接健康和可用指标；
2. 一台业务设备可以关联 1 个主设备和多个子传感器，主设备/子设备角色在页面上清晰可理解；
3. 用户至少选择一项有效指标，指标名称、单位、来源、有效期和适用场景可查看；
4. 已被其他业务设备使用的来源设备，提交时明确提示占用对象和换绑影响，不能静默覆盖；
5. 配置修改形成可追溯版本，显示生效时间、适用设备和受影响的监控、报警、报表及 OEE；
6. 来源设备或指标失效时，页面明确提示数据影响和迁移/重新配置入口；
7. 配置完成后能够从设备详情、运行监控、报警和 OEE 返回查看当前绑定状态。

技术实现可由宿主平台完成访问控制和服务端校验；本系统产品验收只关注用户能否完成绑定、理解影响并追踪结果。

### 5.2 数据接入总览应让运维人员知道“发生了什么、影响什么、如何处理”

当前“手动拉取”和“补偿重放”有任务入口，但产品上不能只反馈“提交成功”。用户需要看到任务范围、任务编号、当前进度、成功/失败数量、失败原因、是否影响监控/报警/OEE，以及重试、暂停或人工结束入口。

建议为接入任务建立统一的用户状态：

```text
已创建 → 执行中 → 成功
                 ↘ 部分成功 → 可重试
                 ↘ 失败 → 待处理/重试中
补偿中 → 补偿成功 / 部分成功 / 人工终止
```

任务详情至少要能回答：谁在什么时间对哪些设备和指标执行了什么操作；哪些数据成功、失败或跳过；失败是否影响 OEE、报警和报表；下一步由谁处理。

### 5.3 实时和历史数据链路必须在界面上可见

用户需要知道当前看到的是实时数据、延迟数据还是历史快照，以及数据多久没有更新。产品上应显示订阅中、轮询降级、连接中断、数据延迟、最后收到数据时间和统计截止时间，并在异常时给出处理建议。

不能只更新时间文本而不更新设备数据。当前 `RealtimePage` 的 5 秒定时器主要更新时间，设备数据仍来自静态数组；在演示版本可以保留静态数据，但应明确“演示/静态模拟”，避免用户误以为设备状态正在实时变化。

如果现场数据暂时不可用，系统应区分“设备未联网”“已联网但暂时无数据”“数据延迟”“设备确实处于停机/故障”，并说明这几种状态对报警和 OEE 的影响。

### 5.4 数据质量、缺失和补偿要有运维闭环

数据质量不能只作为一个颜色或标签展示。设备管理员和 IoT 运维人员应能看到异常发生在哪台设备、哪个指标、哪个时间段，对运行监测、报警和 OEE 造成什么影响，以及应该重试、补传、忽略还是人工确认。

建议至少区分正常、待确认、质量异常、未连接、数据延迟、补传中、补传完成和无法恢复等用户状态；缺失区间、重复数据、乱序数据和补传数据都应有可追踪的处理结果。数据不足时，运行监测和 OEE 应显示原因，不应把缺失值当成 0 或设备故障。

“数据完整率”还要说明统计范围，例如未配置指标、不支持指标和不适用设备不应被算入应采样范围。

### 5.5 不同数据要有不同的业务解释

平台提供的实时指标、状态、产量、报警、维修和质量数据，不能全部用同一种“平均值”展示。用户应能理解：温度/压力等指标看趋势和极值，状态看持续时间，计数器和产量看增量，报警看次数和持续时间，维修看工单状态和处理时长，质量看有效与异常数据范围。

OEE 页面尤其要说明统计窗口、班次归属和数据质量影响，避免用户把不同时间范围或不同设备口径的数值直接比较。

## 六、报警中心设计必须统一的逻辑

### 6.1 先统一报警状态机和恢复口径

报警要让值班人员清楚知道“是否需要我处理、谁正在处理、设备是否已经恢复、为什么还没有关闭”。建议正式采用：

```text
候选 → 已触发 → 已确认 → 处理中 → 已恢复待关闭 → 已关闭
```

允许的分支：

- 候选期间条件中断：回到无活动事件，不产生正式报警；
- 条件恢复：进入恢复待关闭或自动关闭，必须二选一并全系统一致；
- 维修完成：回写处理结果，是否自动关闭由规则决定；
- 人工关闭：必须记录原因、恢复依据和关闭人的业务上下文；
- 已关闭事件禁止直接重开，重新触发生成新事件并关联历史事件。

当前需要产品负责人统一确认的矛盾是：需求细则、页面注释和演示状态对“自动恢复后是否直接关闭”存在不同表达。应按报警类型定义规则：温度/压力等阈值类通常恢复后待确认，通信/数据质量类可在稳定恢复后自动关闭，程序不一致和维修关联故障需要人工确认；无论采用哪种方式，都要保留恢复记录和关闭依据。

### 6.2 确认、处置和关闭的必填项必须与业务动作上下文一致

用户每完成一个动作，都应知道记录了什么、下一步交给谁、什么时候需要再次处理。建议：

- 确认：确认人、确认时间、确认说明、接管责任；
- 处置：处置方式、措施、预计完成时间、处理人；转维修时生成或关联唯一维修单；
- 关闭：恢复证据、关闭原因、关闭人、关闭时间；是否允许人工强制关闭及其业务条件由宿主平台传入的动作上下文控制；
- 状态变化后立即在报警列表、设备详情、工作台和关联维修单中同步显示；
- 并发或重复操作时给出明确冲突提示，不应出现“页面提示成功但状态没有变化”。

### 6.3 报警和维修不能各自维护“处理人”

报警责任人、维修负责人和班组监督人不是同一个角色。用户需要在报警详情中区分三者，并能看到当前任务由谁接管、维修到哪一步、是否逾期。

当报警“转维修”时：

1. 报警详情显示对应的维修申请/工单；
2. 维修工单带入设备、故障现象、触发时间、严重度和报警证据；
3. 派工、改派和维修结果在维修模块维护；
4. 维修状态回写报警事件和设备履历；
5. 报警关闭前检查维修是否完成、设备是否恢复，或是否满足宿主平台提供的人工关闭业务条件。

产品上应明确：一条报警默认生成一张主工单；确需拆分时，用户能看到主工单与子任务关系，避免重复派工或重复统计。具体可执行动作由宿主平台提供的业务动作上下文控制。

### 6.4 通知策略要让用户看到“是否送达、谁在处理、是否升级”

通知策略页面不能只配置渠道和模板。报警详情、通知记录或消息中心应能看到实际接收人、发送/送达时间、失败原因、重试状态、升级节点和静默期命中情况。

这样值班人员才能判断是规则没有触发、消息发送失败、接收人没有确认，还是已经转交升级对象；通知失败时要有重试或人工处理入口。

## 七、维修管理和备件管理闭环调整

> 本节分析维修和备件；不展开点检、巡检、保养的内部设计。若它们产生异常，需要复用同一维修/备件闭环。

### 7.1 维修对象必须统一，用户要能从报修走到验收

当前待维修、故障报修、维修任务、维修详情的页面链路已经存在，但用户需要在每一步明确知道任务状态、负责人、截止时间和下一步动作。建议统一主流程：

```text
报修草稿 → 已提交/待派工 → 已派工 → 维修中 → 待验收 → 已完成
```

旁路状态：

- 已取消：必须填写原因，并说明是否需要重新报修；
- 已挂起：填写原因和预计恢复时间，恢复后回到原任务；
- 返修/重新打开：保留原工单和历史验收记录，不覆盖已完成记录。

工单详情至少要让用户查看：来源（人工报修/报警/其他异常）、设备和位置、故障现象与等级、影响生产和停机时间、负责人和协作人、故障原因、维修措施、验证结果、附件、关联报警、备件领用和维修履历。

### 7.2 明确响应、维修和停机时长，让报表能支持管理决策

用户看到“维修时长”“响应时长”时，应知道它具体从哪个时间点算到哪个时间点。建议在页面和报表中分别展示：

- 响应时长：报警/报修 → 首次确认或接单；
- 派工时长：报修 → 派工；
- 等待维修时长：报修 → 开工；
- 维修作业时长：开工 → 维修完成；
- 总故障时长：故障开始 → 设备恢复；
- 生产停机时长：实际影响生产的停机区间；
- MTTR、MTBF 的定义、统计范围和是否排除计划停机。

不要只显示“维修总时长”一个无法解释的数字；管理者应能从统计结果下钻到具体工单和设备。

### 7.3 维修完成必须有验收，而不是填写结束时间即完成

维修人员提交维修结果后，应进入待验收状态。验收人需要看到故障原因、处理措施、实际工时、备件、设备当前状态、验证结果和关联报警，并能通过、退回返修或依据宿主平台提供的业务动作上下文处理特殊关闭。重要/紧急故障的验收动作由宿主平台业务规则决定，验收结果回写报警、设备履历、停机和 OEE 相关损失记录。

### 7.4 备件管理要让“申请—领用—退库—库存—成本”闭环

备件页面不应只显示库存数字。仓库人员和维修人员需要知道申请数量、预留数量、实际出库数量、退库数量、当前可用库存和对应维修工单。

建议采用以下用户流程：

```text
领料申请 → 待审核/待预留 → 已出库 → 使用/退库 → 工单结算
入库申请 → 待审核 → 已入库 → 盘点/调整（如有差异需留痕）
```

出库不能超过可用库存，超领需满足宿主平台提供的业务动作条件；维修取消或剩余物料应支持退库；库存预警应引导用户查看补货或处理路径，不应直接表示采购已经完成。库存、维修成本、设备履历和业务单据流水应能相互追溯。

## 八、OEE、报表和大屏的范围调整

### 8.1 OEE 作为标准版核心能力，重点优化“可解释、可下钻、可行动”

OEE 已经属于当前标准版功能范围。本次评审不讨论是否上线 OEE，而是判断现有 OEE 是否足以帮助管理者发现问题、理解原因并采取行动。OEE 页面不能只展示一个百分比或排名，必须让用户回答三个问题：**哪里低？为什么低？下一步做什么？**

建议保留并完善现有的实时、历史、详情、速度配置和计划停机能力，形成以下产品链路：

1. **总览层**：展示 OEE、可用率、性能率、合格率、目标值、趋势和异常标识；支持按设备、产线、车间、班次、日期和物料/工单筛选。
2. **指标下钻**：点击 OEE 可进入三项组成指标；点击可用率进入计划停机、故障停机、待机、离线和维修停机；点击性能率进入标准节拍/理想速度、实际速度、运行时间和产量；点击合格率进入良品、不良品及质量原因。
3. **原因解释**：低于目标时，页面应列出贡献最大的停机、报警、维修、速度损失或质量损失，并提供进入对应明细的入口，而不是只显示红色百分比。
4. **行动闭环**：从 OEE 异常可以进入报警处置、维修工单、计划停机调整、速度配置或质量问题记录；完成处理后能够在趋势和设备履历中看到结果。
5. **配置反馈**：速度、标准节拍、班次、生产日历和计划停机的修改，应明确适用设备/产线、开始生效时间、影响的统计范围和变更记录。用户要知道“改了什么、从什么时候开始影响 OEE”。

OEE 的基础口径至少应在页面中可查看或通过帮助说明获得：

- 可用率、性能率、合格率和 OEE 的定义及计算关系；
- 计划停机是否从负荷时间中扣除，故障停机、待机和离线如何分类；
- 标准节拍/理想速度的单位、适用范围和版本；
- 产量、良品和不良品的来源及班次归属；
- 日、班次、周、月汇总采用的统计方式。

数据不足时必须用用户能理解的状态区分“暂无生产数据”“配置未完成”“数据质量不足”“不适用”，不得让用户把缺失数据误读成 0% 或设备性能为零。演示环境可以使用示例数据，但页面仍应体现这些状态和产品规则。

计划停机也应与 OEE 建立清晰的用户语义：用户需要知道计划停机是从可用率损失中扣除，还是作为负荷时间排除；同时能够查看计划与实际停机的偏差、取消/变更记录，并能从 OEE 低点回到对应停机明细。

### 8.2 报表要让用户“看懂结果、找到原因、带走结论”

当前报表覆盖范围较广，但用户更关心的是：这个指标代表什么、统计的是哪段时间、为什么与其他页面不同、下一步应进入哪里。建议每个报表统一提供：

- 指标名称、业务定义和统计范围；
- 当前筛选条件、数据截止时间和演示/真实标识；
- 无数据、数据不足、未配置和不适用等空态说明；
- 从汇总到设备、班次、报警、维修、停机或质量明细的下钻入口；
- 导出当前筛选范围，并在导出结果中保留时间和口径说明。

报表主题可优先收敛为运行/状态、OEE、报警、数据质量、维修和库存几类，其他内容作为这些主题的下钻或后续扩展。用户点击“查询”后应看到结果变化或明确的演示反馈，不能让按钮看起来可用但没有任何结果。

### 8.3 大屏要明确服务对象、数据状态和安全边界

大屏适合公开展示生产运行概况，但不能与管理总览、实时监控承担相同职责。产品上应明确：

- 面向领导、访客还是现场值班人员；
- 只读展示哪些指标，是否隐藏敏感信息；
- 与后台访问入口是否由宿主平台控制，展示范围和只读业务动作如何管理；
- 设备、报警、OEE 和数据质量是否保持同一口径；
- 数据中断、延迟或使用演示快照时如何提示；
- 轮播、暂停、分页和导出分别解决什么场景。

演示阶段可以固定展示布局，但不能让固定设备数量或旧版大屏入口成为产品逻辑。

## 九、平台公共服务依赖与本系统业务履历

### 9.1 依赖平台提供用户、组织范围与业务动作上下文

宿主平台负责统一用户身份、账号状态、会话、组织/角色/业务动作标识、数据范围和平台级通用日志。本系统不重复建设这些基础能力，也不创建独立的登录、权限、审计或平台日志模块。本系统只消费宿主平台传入的当前用户、组织/设备范围、可执行业务动作标识和宿主跳转信息，用于展示页面、启用/禁用业务动作并回写业务结果。

### 9.2 业务页面消费平台上下文，不维护公共管理对象

本系统不维护独立的用户、角色矩阵、权限管理页面、登录会话或平台日志规则。需要与宿主平台对齐的是业务动作标识和上下文契约，例如查看、新增、编辑、提交、审核、发布、执行、导出，以及确认/关闭报警、派工/改派、维修验收、库存审核、OEE 配置和规则发布。若上下文缺失、过期或不允许动作，页面应明确显示不可执行原因，不得伪造成功。

### 9.3 业务履历与平台通用日志分工

宿主平台记录登录、身份、权限变化和通用平台日志。本系统不建设独立的操作审计模块，但必须保留业务对象自身的过程履历，保证用户在业务页面理解当前进展和历史结果。至少覆盖：

- 设备新增、变更、停用、报废和联网换绑的业务履历；
- 指标选择、报警规则和通知策略变更的版本与生效信息；
- 报警确认、处置、关闭和批量操作的处理记录；
- 维修派工、改派、取消、完成、验收和返修的工单履历；
- 库存入库、出库、退库、调整和审核的业务单据流水；
- OEE 标准节拍、速度、班次、计划停机和目标变更的配置履历；
- 数据补偿、报表导出等业务操作的结果信息。

平台级日志用于追溯通用操作，本系统业务履历用于解释报警争议、维修责任、库存差异和 OEE 口径变化；两者不重复建设。

## 十、跨模块闭环矩阵

| 起点 | 必须联动 | 结束条件 | 必须回写 |
|---|---|---|---|
| 设备台账新增/变更 | 绑定、文档、报表范围 | 档案启用且主数据完整 | 设备履历 |
| IoT 绑定启用 | 指标选择、健康检测、规则、监控 | 绑定生效且指标可用 | 绑定版本、影响范围 |
| IoT 数据中断 | 数据质量、通知、报警、补偿 | 数据恢复并完成质量确认/补偿 | 质量事件、任务结果、报警状态 |
| 指标超限/状态故障 | 报警中心、通知、维修 | 条件恢复且完成处置 | 报警流水、维修关联、设备履历 |
| 报警转维修 | 待派工、派工、维修、验收 | 工单完成/取消并满足关闭条件 | 报警状态、设备履历、统计 |
| 维修领料 | 备件预留、出库、退库 | 单据审核且数量与工单一致 | 库存流水、维修成本 |
| 库存低于安全库存 | 预警、采购申请（若在范围内） | 补货入库或授权关闭 | 库存事件、关闭依据 |
| 程序比对不一致 | 处理记录、报警、维修/MES | 处理结论和证据完整 | 比对状态、报警 |
| 设备停用/报废 | 绑定、规则、监控、报表 | 无新数据消费且历史可查 | 状态履历、影响范围 |

点检、巡检、保养本次不评审内部流程，但其异常项若转维修、产生备件领用或触发报警，必须接入上表的维修、库存、报警公共对象，不能另建一套“孤立工单”。

## 十一、标准版 V1 建议范围（MoSCoW）

### Must：标准版核心闭环与 OEE 基础能力

1. 设备管理员、生产/班组、维修、仓库和管理角色能够按职责完成查看、处理、审核、验收和分析；
2. 统一设备主数据、设备状态、组织、责任人、档案和履历，并让资产、监测、报警、OEE、维修和报表能够回到同一设备；
3. IoT 绑定：1 主 + N 子、平台验证、指标选择、启停、换绑、影响范围提示和操作留痕；
4. 运行监控能够让用户区分运行、待机、故障、离线、延迟和无数据，并看到最后数据时间；
5. 报警最小闭环：触发、确认、处置、恢复、关闭、通知、升级、去重、转维修和业务履历；
6. 报警与维修工单唯一关联，维修过程支持派工、接单、维修、备件、停机、验收、完成/取消、返修和履历；
7. 备件主数据、入库、出库、退库、库存流水、安全库存和与维修工单关联；
8. **OEE 当前功能可用且可解释**：实时/历史/详情分析、可用率/性能率/合格率及 OEE、目标值、趋势、设备或产线筛选、异常状态和基础下钻；
9. **OEE 配置闭环**：标准节拍/理想速度、班次/生产日历、计划停机、产量及质量口径有明确入口、生效时间、适用范围和变更记录；
10. OEE 能够从低指标定位到停机、报警、维修、速度损失或质量损失，并进入对应明细或处理入口；
11. 关键报表支持查询、空态、口径说明、下钻和当前筛选范围导出；
12. 平台提供认证、组织/设备范围和接口访问控制；本系统保留业务操作失败反馈、业务履历和关键操作结果回显；
13. 点检、巡检、保养本次不展开内部设计，但其异常转报警、维修或备件时复用公共对象和状态回写。

### Should：核心能力上线后的增强

1. 运行时长、设备状态、报警、维修、质量、库存和 OEE 专题报表；
2. OEE 目标管理、设备/产线排名、班次对比、趋势对比和损失 Pareto；
3. OEE 与报警、维修、停机、质量的跨模块联动和改善前后对比；
4. 数据接入运维看板、缺失明细、死信处理和补偿明细；
5. 文档库、维修经验库与设备/工单关联；
6. MES 程序比对（前提是基线和实际参数来源已书面确认）；
7. 通知模板、值班日历和多级升级；
8. 批量导入、异步导出、二维码和消息中心。

### Could：后续增值能力

1. 报警规则模板批量应用、组合规则、速率规则和波动规则；
2. 高级大屏、跨车间对比和趋势预测；
3. 移动端、扫码和现场离线执行；
4. 设备健康评分和预测性分析。

### Won’t：当前标准版明确不做或不承诺

1. 本系统直接连接 PLC、网关或维护底层协议/点位；
2. 在本系统长期复制 IoT 原始时序作为第二个 IoT 平台；
3. 远程控制设备或远程下发未经确认的控制指令；
4. 在没有明确数据来源、时间口径和质量状态时，不对实时报警或 OEE 的时效性与可解释性作无依据承诺；
5. AI 预测性维护；
6. 跨工厂、跨租户共享 IoT 来源设备（除非单独设计授权和统计归属）；
7. 采购、到货验收、安装调试、设备变更、报废处置等完整资产供应链功能——除非合同明确属于本期，否则应列为后续阶段，而不是通过菜单预留暗示已交付；
8. 点检、巡检、保养内部功能的重新评审和扩展，本次仅保留与报警、维修、备件的接口边界。

## 十二、关键状态机建议

### 12.1 设备资产

```text
草稿 → 已启用 → 闲置
             → 停用 → 已启用（经授权恢复）
             → 报废/归档
```

规则：有历史引用后禁止删除；停用/报废必须影响绑定、规则、监控和业务报表，并保留历史查询。

### 12.2 绑定配置

```text
待配置 → 校验中 → 草稿 → 待生效 → 已启用 → 已停用
                                      ↘ 换绑（旧版本关闭，新版本生效）
```

健康状态独立于配置状态：

```text
正常 ↔ 延迟 ↔ 部分中断 ↔ 数据中断 → 恢复/补偿
```

### 12.3 接入任务

```text
已创建 → 执行中 → 成功
                 ↘ 部分成功 → 可重试
                 ↘ 失败 → 重试中
补偿中 → 补偿成功 / 部分成功 / 人工终止
```

### 12.4 报警事件

```text
候选 → 已触发 → 已确认 → 处理中 → 已恢复待关闭 → 已关闭
```

必须明确自动恢复是否直接关闭；不要在不同页面采用不同口径。

### 12.5 维修工单

```text
报修草稿 → 待派工 → 已派工 → 维修中 → 待验收 → 已完成
                         ↘ 挂起              ↘ 返修
                         ↘ 已取消
```

### 12.6 备件单据

```text
入库：草稿 → 待审核 → 已入库 → 冲销/作废
出库：草稿 → 待审核 → 已出库 → 退库/冲销
调整：申请 → 审批 → 已生效
```

库存数量必须由已生效单据和调整流水计算。

## 十四、产品验收建议

### 14.1 不能以“页面打开”作为验收

每个功能至少验证四层：

1. **页面层**：字段、平台上下文控制下的业务动作可见性、空态、异常提示和下一步入口符合角色任务；
2. **操作层**：点击查询、保存、确认、转维修、派工、领料、验收、下钻和导出后，用户能看到明确结果；
3. **业务层**：状态、时间、关联关系、OEE 口径、组织范围上下文和业务动作结果符合产品规则；
4. **闭环层**：下一业务环节能接收、处理、回写，历史记录可追溯。

演示数据可以与真实现场数据不同，但不能用数据不一致掩盖按钮无反馈、状态不变化、入口断裂或结果无法解释。

### 14.2 核心用户场景验收

- 设备管理员完成一台业务设备与 IoT 主设备/子传感器的绑定，看到验证结果、指标选择、影响范围和生效状态；
- 生产人员从总览或实时监控发现故障/离线/数据延迟，进入报警详情并完成确认、处置或转维修；
- 维修人员接单、填写维修结果、申请/领用备件，提交验收后，报警、设备履历、停机和库存状态同步更新；
- 管理者从 OEE 低指标进入可用率、性能率、合格率及主要损失原因，再进入对应停机、报警、维修或质量明细；
- 用户查看没有生产数据、配置不完整、数据中断或不适用设备的 OEE 时，看到明确原因和下一步入口，而不是 0%；
- 用户修改标准节拍、理想速度、班次、计划停机或 OEE 目标后，看到适用范围、生效时间、影响范围和历史记录；
- 设备、报警、维修、OEE、库存和统计数据是否处于宿主平台传入的组织范围上下文内；
- 查询、筛选、下钻、返回和导出均保留当前业务范围并给出明确结果；
- 取消、挂起、失败、重试、返修和人工强制关闭等异常分支有可理解的处理路径。

### 14.3 当前演示版本需要明确的标识和反馈

在真实数据接入前，所有页面建议统一显示：

- 演示数据/真实数据；
- 数据更新时间、统计截止时间或演示快照时间；
- 数据来源和是否为静态模拟；
- 操作是否仅在本次演示生效，或已经写入系统；
- 不可执行的按钮应禁用或标明“原型占位”，不能让用户以为操作已生效。

尤其应保证实时监控、联网配置、报警、维修、库存、报表、OEE 和大屏的操作路径都有明确反馈。演示数据可以静态，但用户点击查询、保存、确认、转维修或下钻后，页面必须能说明结果和下一步。

## 十六、补充的高风险闭环问题

以下问题并非要求现在把演示系统做成完整生产系统，而是需要在产品需求中明确，避免标准版上线后出现用户不知道怎么处理、状态无法解释或模块之间互相矛盾的情况。

### 16.1 报警自动建单、故障主线和 SLA 需要形成用户可理解的闭环

旧版维修任务原型明确表达了“监测异常报警后自动生成检修任务”，而当前标准版更接近由用户选择“转维修申请”后发起工单。两种方式都会影响值班人员的工作方式，应在产品规则中明确：哪些报警自动建单，哪些报警由人员判断后转维修；用户必须能在报警详情看到建单方式、负责人和当前工单状态。

如果要求自动建单，至少应支持：

- 适用的报警等级/规则和建单类型；
- 负责人队列、责任班组和接管人；
- 同一活动故障只生成约定数量的工单，并能识别重复报警；
- 建单失败时显示失败原因、重试入口或转人工处理；
- 自动建单状态与报警事件双向可见。

- 同一台设备可能产生多条报警，也可能关联一张主工单和多个维修任务。产品上应提供“故障主线”视图，将相关报警、报修申请、维修工单、维修记录和验收结果串在一起，避免维修人员重复处理同一故障。

SLA 也不能只显示“升级节点”。至少要让用户看到首响、接单、派工、到场/开工、恢复和关闭等关键时限，知道当前是否逾期、由谁负责、暂停依据是什么，以及逾期后下一步如何升级。

### 16.2 通知、停机和报表必须围绕同一业务事实

用户需要能够回答“报警是否通知到人、设备实际停了多久、这段损失是否进入 OEE、维修是否改善了结果”。因此，通知、停机、OEE 和报表不能各自维护互不关联的结果。

通知策略除了配置渠道、通知组、重复间隔和升级节点，还应在报警详情中提供发送状态：实际接收人、发送/送达时间、失败原因、重试状态、升级是否触发和静默期是否命中。这样值班人员才能判断是没有触发规则、发送失败，还是接收人未处理。

计划停机、故障停机、维修停机、换模和数据中断等情况应形成统一的停机记录，并能关联设备、报警、维修工单、班次和计划。用户需要看到计划与实际的差异、重叠停机如何处理，以及该停机在 OEE 和运行报表中的影响。计划停机应补充结束时间、跨天、适用设备、重叠、审批、取消和变更等业务规则。

### 16.3 数据来源、筛选和失败反馈不能让用户误以为“已经生效”

当前大量页面使用演示数据，这是演示系统允许的做法；但页面必须明确当前是演示还是实际数据，并让用户知道操作结果是否仅在当前页面有效。切换数据模式或显示“真实数据”标签，不能代替真实请求成功的证明。

需要重点处理以下用户体验断点：

- 实时监控刷新时应说明数据是否真的更新，并显示最后数据时间；
- 报表查询后应改变结果或明确提示当前为演示查询；
- 报警、联网配置、维修、库存和规则操作后，应显示状态、影响范围和下一步入口；
- 质量异常、缺失数据和死信应有查看、处理、重试/放弃和结果反馈入口；
- 无效详情参数应显示明确空态或错误，不应跳到第一条记录；
- 旧版与新版大屏应合并或明确唯一用途，避免用户从不同入口看到不同结论。

演示阶段可用本地状态模拟上述路径，但按钮、标签和提示必须诚实表达“仅演示”还是“已生效”。

### 16.4 备件、指标和平台边界要让业务人员能够正确操作

备件出库时，用户需要按仓库看到可用库存、预留、已出库和可退库数量，并能把领料和维修工单关联起来；不能让用户只看到一个无法解释的总库存数字。库存不足、超领、退库和盘点差异都应有明确的审批或处理路径。

平台指标、指标字典和报警模板对同一指标的名称、单位和适用范围应保持一致。用户选择指标时应看得懂它来自哪个设备、当前是否有效、会影响哪些监控、报警和 OEE 结果；指标变更应保留历史配置和生效时间。

### 16.5 是否建设边缘能力必须先定用户边界

当前标准版更适合定位为消费既有 IoT 平台数据的设备业务系统，不应让客户误以为本系统同时负责 PLC、网关、协议和边缘节点运维。如果项目未来建设边缘能力，应单独定义边缘站点、断网缓存、恢复补传、设备身份、远程配置和升级记录等范围；否则应在菜单、产品说明和验收边界中明确“不包含底层采集和远程控制”。

### 16.6 角色职责与页面结构需要收敛

建议至少区分设备管理员、IoT 运维、生产/车间管理员、班组长、维修人员、仓库管理员、管理者等业务使用者，并明确其业务任务、交接关系和平台上下文所需的业务动作标识。

申请与审核、规则编辑与发布、维修执行与验收、出入库与盘点的业务职责不应在页面上混为一谈，具体动作由宿主平台提供的上下文控制。工作台、监测总览、实时监控和大屏应分别服务待办、管理总览、设备处置和展示；同一指标在不同页面的点击入口和筛选结果应保持一致。

点检、保养、巡检本次不展开内部设计，只要求它们产生的异常能进入统一报警/维修/备件闭环，避免形成孤立任务。

### 16.7 验收应写成 Given / When / Then，并以用户任务是否完成为核心

除页面是否打开外，验收还应覆盖四个层次：

- **用户任务**：业务使用者能否完成发现问题、确认、处置、派工、维修、领料、验收和分析；
- **业务闭环**：每类单据从创建到终态，并验证取消、挂起、失败、重试和返修分支；
- **数据与组织上下文**：状态、时间、质量、版本、关联关系和宿主平台传入的组织范围符合产品规则；
- **可运营性**：失败反馈、通知送达、操作留痕、演示/真实标识和关键性能符合约定。

建议至少增加以下 OEE 验收场景：

```text
Given 某设备在选定班次内有 OEE 数据且低于目标值
When 管理者点击 OEE 结果
Then 页面展示可用率、性能率、合格率及主要损失原因，并可进入对应停机、报警、维修或质量明细
```

```text
Given 某设备没有生产数据或 OEE 配置不完整
When 用户查看实时或历史 OEE
Then 页面显示暂无数据/待配置/不可计算等原因，不显示 0% 并给出下一步配置或处理入口
```

```text
Given 用户修改某产线的标准节拍或计划停机
When 保存配置
Then 页面显示适用范围、生效时间、影响的 OEE 统计范围和变更记录，历史期间不被无提示地改写
```

还应保留报警、维修、库存、数据恢复和宿主平台动作上下文等场景，例如：报警关联未验收工单时，页面依据平台传入的业务动作条件给出不可关闭或需补充条件的明确反馈；维修领料和退库能回到库存与工单；重复补偿不会让报警或库存重复。

## 十七、演示数据与产品口径的复核风险

本节只讨论演示数据可能对用户理解造成的产品风险，不把演示数据与真实生产数据不一致本身作为缺陷。
### 17.1 演示数据的使用边界

当前系统是演示版本，设备数量、名称、日期和部分指标在不同页面之间不完全一致，属于演示素材的正常特征。本报告不把这些差异本身作为产品缺陷，也不要求用演示数据完成生产级财务或运营对账。

但演示页面仍应让用户能够正确理解产品规则。以下情况需要在产品层处理：

- 同一页面前后操作后状态含义发生变化，用户无法判断操作是否生效；
- 缺少“暂无数据、未配置、数据中断、不适用”等状态，导致用户把示例值理解为真实结论；
- OEE、报警、维修、停机之间的入口和状态无法形成可理解的业务链；
- 筛选、下钻、导出或返回操作表现为可用，但实际没有反馈或结果变化。

生产版本再根据确认后的指标定义统一事实来源、统计窗口和汇总口径。当前演示数据仅用于说明页面结构和用户操作路径，不作为验收数据基线。

### 17.2 OEE 产品口径必须可见、可解释

OEE、可用率、性能率和合格率的期间汇总，应按照已确认的业务定义和相应权重计算，不能无条件对每日百分比做算术平均。数据不足、无生产、配置未完成或不适用时，应显示“暂无数据/不可计算/待配置”等明确状态，而不是显示 0%。

对标准节拍、理想速度、运行时间、产量、良品/不良品、班次、计划停机和故障停机的定义，应在 OEE 页面或帮助说明中可查，并且配置变更要显示生效时间和影响范围。产品验收应验证用户能从 OEE 结果下钻到停机、报警、维修、速度或质量原因，而不是要求演示数据逐项对账。

### 17.3 设备生命周期应拆成独立状态轴

台账中的一个“设备状态”不能同时表达资产生命周期、通信健康、维修锁定和生产可用性。建议至少拆分：

- 资产生命周期：草稿、在用、闲置、停用、报废/归档；
- 配置/绑定状态：未配置、待生效、已启用、换绑、已停用；
- 通信健康：正常、延迟、部分中断、数据中断、未知；
- 维修锁定：可维修、维修中、待验收；
- 生产可用性：可生产、计划停机、故障停机、待料、未配置。

这些状态由不同事实来源驱动，不能用一个前端下拉框任意互相覆盖。

## 十八、功能裁剪与交互一致性建议

### 18.1 资产台账要表达清晰的生命周期

台账当前提供设备状态、联网、OEE、日期、附件和子设备等信息，但用户还需要知道设备从启用到停用、报废或归档的变化，以及这些变化对监控、报警、维修和 OEE 的影响。

采购申请、到货验收、安装调试、调拨、维保合同和财务资产关联等是否属于本期，应在合同和产品范围中明确。如果不属于本期，应列为后续阶段，不要用一个“设备状态”下拉框模拟全部生命周期。

已产生监测、报警、工单或库存履历的设备应使用停用/归档/报废，保留历史查询，不允许通过删除让业务记录消失。

### 18.2 应收敛重复的信息架构，并处理“看起来能用”的入口

当前工作台、总览、实时监控、大屏之间存在 KPI 和异常列表重复；报警规则、规则模板、版本页面存在配置边界重叠；多个报表主题存在指标重复。建议标准版建立清晰的页面职责：

- 工作台：待办、提醒和快捷入口，不重复承载完整 KPI；
- 监测总览：全局状态、趋势、OEE 概况和异常下钻；
- 实时监控：设备级实时状态和处置入口；
- 大屏：独立只读展示，面向领导/访客或现场展示，使用同一业务口径；
- 报表：围绕运行/OEE、报警、数据质量、维修和库存组织，其他内容作为下钻或后续扩展；
- 报警规则与版本：在规则详情中清晰呈现版本和发布影响，通知策略作为运维配置保留。

查询、导出、重算、保存、删除、派工、验收、库存出入库、规则发布和大屏控制等入口，在完成真实闭环前应明确标注“仅演示/原型占位”，或者提供完整的演示反馈，避免用户把提示信息误认为已经生效。

### 18.3 统一详情页和筛选行为，让用户不会“从 A 进入却看到 B”

同类页面应保持一致的详情、返回、保存和取消语义。用户从设备、报警、OEE、计划或工单进入详情时，应看到与入口相符的对象；参数无效时显示明确空态或错误，不应自动跳到第一条记录或展示全量明细。

设备、报警、维修、OEE 和报表之间的跳转要保留设备、组织、时间、班次、产线、物料和状态等筛选条件，并提供返回上一级的路径。筛选、查询、重置、下钻和导出应对当前范围有明确反馈；OEE 下钻尤其要保留当前指标和统计周期。

### 18.4 字典、筛选和摘要信息要让用户看到一致结论

设备类型、指标、仓库、报警状态、工单状态和组织范围应有统一的业务名称。用户在不同页面选择同一个条件时，应得到一致的设备、任务和统计结果；缺少分类、编码或状态时，应明确提示，而不是出现空列表或看似成功的筛选。

报警中心摘要、工作台待办、监测总览卡片和 OEE 汇总应来自相同的业务范围和统计截止时间。演示版本可以使用不同样例数量，但页面不能用静态数字掩盖筛选无效、摘要不更新或下钻对象不一致等问题。

建议为每个指标、状态和字典项明确显示名称、适用范围、统计含义和更新时间，避免用户只看到一串无法理解的编码。

### 18.5 产品规格与当前演示体验存在偏差

`src/specs/pageSpecs.jsx` 中已经表达了一些用户体验目标，建议在产品验收矩阵中逐条确认，而不是只停留在规格文字中：

- 总览和实时监控是否能让用户看到刷新状态、最后数据时间和失败提示；
- 摘要卡点击后是否进入对应筛选结果；
- 报警确认、处置、关闭是否有必填提示、状态变化和下一步入口；
- 历史 OEE 是否支持月份等常用筛选、趋势查看、损失下钻和当前范围导出；
- 速度/标准节拍配置是否仅对适用设备或产线生效，并明确生效时间；
- 实时监控是否按严重度和通信/运行状态正确筛选，离线或无数据设备不应误显示为正常运行；
- 总览、实时监控、大屏和 OEE 是否显示一致的统计截止时间，并区分演示快照与真实实时状态。

当前演示版本可以使用静态数据，但必须通过标签和反馈说明数据性质；生产版本则应让用户看到实际数据来源、更新时间、质量状态和统计截止时间。

## 十九、最终产品结论

当前功能设计的主要问题不是“页面少”，而是**页面很多，但核心对象、状态、数据源和责任边界尚未真正闭合**。

建议后续开发遵循三条原则：

1. **先统一用户任务和对象，再扩展页面。** 先让设备、来源设备、指标、报警、故障、工单、停机、库存和 OEE 能够围绕同一设备被用户连续理解和操作；
2. **把 OEE 与报警、维修、停机、质量放在同一改善闭环中。** OEE 不是孤立的统计页面，低指标必须能解释原因并进入处理入口；
3. **先完成关键闭环，再增加高级分析。** 基础报警、维修、备件、停机、OEE 和履历要可用、可追踪、可验收，再扩展预测性维护、复杂算法和集团级分析；
4. **先明确数据语义，再承诺实时性和指标可信度。** 用户应知道数据来源、更新时间、质量状态和统计截止时间，不能以演示标签或单一百分比替代解释。

如果按本报告调整，建议将“标准版”定义为一个**可配置、可追溯、可恢复、具备完整业务履历的设备运营闭环平台**，而不是“把所有菜单都放进去的设备管理页面集合”。
