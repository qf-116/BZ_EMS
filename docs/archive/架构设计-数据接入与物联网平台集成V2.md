## 第一部分：项目背景

### 0.1 本次复审修订摘要

本版本根据架构、工程、安全与可靠性复审意见修订，核心变化如下：

1. 明确本方案是“标准版对接既有 IoT 平台”的目标态；IoT 平台负责设备连接、协议解析、点位配置和原始数据，本系统负责业务绑定、消费配置、聚合读模型、报警事件和业务报表。
2. 将 D1 改为“历史/统计 API 拉取，实时优先订阅；无订阅能力时降级轮询”，并明确降级状态下不得宣称秒级实时报警。
3. 将 D8 改为“短期重算缓冲 + 聚合数据长期保存”，短期缓冲默认保留 7 天、可配置为 7~30 天，不复制长期原始时序。
4. 新增聚合事实表、拉取任务/任务明细、来源设备健康、指标版本、报警事件和 MES 程序比对数据模型。
5. 修正迟到数据处理：按源时间归入原窗口，允许窗口重算，不再写入下一个时间窗口。
6. 将审计、中断检测、幂等、补偿和数据质量纳入一期，不再延后到三期。
7. 增加接口契约最小要求、Owner/责任矩阵、页面迁移清单和可量化验收标准。

### 1.1 项目概况

- **项目名称**：东浩智创 设备管理系统标准版
- **当前形态**：纯前端演示系统（React 19 + Ant Design v6 + Vite 7 单文件构建，双击 index.html 即可运行），内置演示数据
- **未来计划**：该系统将进入真实开发阶段，**本方案按"实际可开发落地"的标准设计**，不是仅演示口径
- **现有功能模块**：工作台、设备资产（设备台账等）、点检管理、保养管理、巡检管理、维修管理、备品备件、数据接入、运行监测（实时监控/OEE/监测大屏）、报警中心、报表中心（含 MTTR/MTBF）、系统管理

### 1.2 公司现有技术环境

公司已有**物联网 IoT 平台**，其职责与现状：

- 负责设备直连与协议解析（采集层）
- 指标、协议等均**已在物联网平台配置完成**
- 设备数据经物联网平台采集、清洗后可供上层系统消费

### 1.3 客户/需求方的原始描述（需求 Origin）

> 目前的系统架构是在公司物联网 IOT 平台获取数据，指标、协议等在物联网平台都配置完成，然后对接设备获取。
> 在本设备管理系统，在设备管理明细中，找到设备并进行联网配置（设备台账列表的操作功能），指定物联网平台中的设备，并获取设备的指标参数，勾选指定参数中部分参数来进行监测和计算统计。
> 另外，实际情况是设备管理系统的一台设备可能会关联物联网平台的多台设备，例如主设备对应物联网的某台主设备 + 多个传感器。
> 因此在进行联网配置的时候，会需要输入主设备编码 + 多个子设备编码。
> 因此，数据接入模块的一些功能可能用不上。

### 1.4 核心诉求

1. 明确设备管理系统与 IoT 平台的系统边界与数据流
2. 评审现有产品架构是否合理、是否有更优方案
3. 确定数据接入模块的调整方案（哪些功能删除、改造、保留、新增）
4. 按真实开发落地标准输出可实施的架构设计

### 1.5 适用范围与文档优先级

本方案仅适用于“设备管理系统标准版对接公司既有 IoT 平台”的集成模式，不覆盖本系统直接连接 PLC、网关或设备协议的采集模式。

在本适用范围内，责任边界如下：

| 系统 | Owner/职责 | 不负责 |
|---|---|---|
| IoT 平台 | 设备连接、协议解析、点位配置、原始时序、源端质量、实时通道、历史明细 | 设备管理业务绑定、报警处置、设备资产和管理报表 |
| 设备管理系统 | 业务设备主数据、绑定实例、指标选择、短期重算缓冲、聚合读模型、派生状态、报警事件、通知、报表和审计 | 设备协议解析、网关配置、点位地址维护 |
| MES | 程序/工艺基线、下发记录及其审批状态；按契约提供生产或程序数据 | IoT 设备连接和本系统报警闭环 |

《设备监测技术设计方案V2.md》和《设备监测实施基线方案V2.md》中与上述边界冲突的“本系统直接采集、原始数据长期入库、点位映射由本系统维护”等内容，必须在开发前同步修订或明确为另一种部署模式。未完成同步前，本方案不得作为开发基线。

## 第二部分：关键决策记录（已逐项确认）

以下决策经与需求方逐项澄清后确认，是 V2 方案的前提。**复审时请重点检验这些决策本身是否合理。**

| # | 决策项 | 结论 | 理由 |
|---|--------|------|------|
| D1 | 数据流向 | **B：历史/统计 API 拉取 + 实时订阅优先**——历史与统计由本系统按窗口调用 IoT API 拉取；实时监控优先消费订阅通道，无订阅能力时降级轮询 | 保持 IoT 平台为数据 Owner；实时展示和批量统计使用不同链路 |
| D2 | 绑定后指标组织方式 | **B：按来源设备分组**——指标清单按「主设备 / 子设备1（温度传感器）/ 子设备2（振动传感器）…」分组展示，组内勾选；统计报表可区分指标来自哪台传感器 | 传感器指标常重名（都有"温度"）；报警与统计需要来源语义 |
| D3a | 联网配置入口形态 | **B：独立配置页**（从设备台账列表「联网配置」操作跳转，非弹窗） | 指标勾选是长清单+分组交互，弹窗放不下；与"简单表单用弹窗、复杂视图用独立页面"的既有约定一致 |
| D3b | 原设备联网配置页去留 | **B：改造成「联网配置总览」**（全部绑定关系+拉取健康度运维视图），网关/协议字段删除 | 网关/协议属 IoT 平台职责；但全局接入状态视图是运维刚需 |
| D4 | 数据接入模块页面取舍 | 生产配置中删除：设备协议/网关/点位映射维护；保留“设备采集能力”作为只读验收矩阵；改造：指标字典→平台指标清单（只读同步）；质量/缺失死信保留为消费质量与补偿运维；**程序参数比对+处理记录保留** | 不能删除用于解释 46 台设备采集边界的能力矩阵；本系统不维护平台点位 |
| D5 | 总览页菜单归属 | **B：移入数据接入组**，数据接入 = 联网配置总览 / 平台指标清单 / 程序参数比对 / 比对处理记录；设备资产组删除原联网配置菜单 | 总览是数据接入运维视图，使用者是实施/运维工程师 |
| D6 | 下游联动深度 | **A：强联动**——报警规则等下游功能的指标选择范围 = 该设备绑定关系中已勾选的指标 | 未勾选的指标没有数据，避免配置出"永不触发的报警" |
| D7 | 实时性方案 | **B：混合模式**——实时监控页优先走 IoT 平台订阅通道；本系统保存实时报警事件和 7~30 天短期重算缓冲；历史数据/统计走周期 API 拉取+本系统聚合落库；无订阅能力时降级轮询 | 订阅适合实时展示，但不能以“只看不存”牺牲报警可追溯性；降级时必须下调实时 SLA |
| D8 | 存储边界 | **A：短期重算缓冲 + 聚合长期保存**——只保存勾选指标的短期规范化样本（默认 7 天，可配置 7~30 天），长期保存分钟/小时/日聚合、状态/报警/质量事实；细粒度长期历史优先透传 IoT 平台 | 控制本系统存储成本，同时支持迟到重算、故障恢复和报警审计；不得假设普通关系库可无规划承载数百台设备 |

## 第三部分：V1 方案概要（评审基线）

### 3.1 分层架构

```
┌─────────────────────────────────────────────────────┐
│ 设备管理系统（应用层）                                │
│  设备绑定关系：系统设备 ⇄ IoT主设备 + N子设备(带角色)   │
│  每台来源设备下勾选监测指标子集                        │
│  ┌────────────┐  ┌────────────┐  ┌───────────────┐  │
│  │ 实时监控    │  │ 统计计算    │  │ 报警引擎       │  │
│  │ 订阅通道透传 │  │ 分钟聚合落库│  │ 基于勾选指标    │  │
│  └────────────┘  └────────────┘  └───────────────┘  │
└─────────────────────────────────────────────────────┘
         │ WebSocket/MQTT 订阅 │ API 周期拉取
┌────────▼────────────────────▼───────────────────────┐
│ 公司物联网平台（采集层 · 原始数据 Owner）              │
│  协议解析 · 点位/指标配置 · 设备直连 · 实时通道 · 历史明细 │
└─────────────────────────────────────────────────────┘
```

### 3.2 边界原则

**原始时序数据的 Owner 是 IoT 平台；本系统只拥有：绑定关系、勾选配置、聚合数据、统计结果、报警事件、业务单据。**

### 3.3 V1 核心数据模型

```
device_binding（绑定关系，一系统设备一条有效记录）
├─ id, device_id（本系统设备）
├─ status: 待配置 / 已启用 / 已停用 / 数据中断
├─ pull_cycle_sec（拉取周期）
├─ last_pull_time, pull_fail_count
└─ binding_version（换绑+1，历史数据按版本隔离统计口径）

device_binding_item（绑定明细：主设备+子设备，一对多）
├─ binding_id, iot_device_code
├─ role: main / sensor
├─ sensor_type（传感器角色：温度/振动/压力…，主设备为空）

device_binding_metric（勾选指标快照，一对多）
├─ binding_item_id
├─ metric_code, metric_name, unit, data_type（平台同步快照）
└─ 唯一键 = (binding_item_id, metric_code)

报警规则指标键 = 设备 + 来源IoT设备编码 + 指标编码
```

### 3.4 V1 依赖 IoT 平台的接口清单

1. 按 IoT 设备编码查询指标清单
2. 设备编码有效性校验
3. 实时数据订阅通道（WebSocket/MQTT）
4. 历史明细查询（透传）
5. 周期批量拉取（按绑定+时间窗）
6. 设备在线状态/心跳查询

### 3.5 V1 模块调整

删除：设备采集能力、点位映射配置；改造：指标字典→平台指标清单、设备联网配置→联网配置总览（移入数据接入组）；保留：程序参数比对、比对处理记录；新增：联网配置独立页（设备台账进入）。

## 第四部分：历史评审发现（V1 → V2.1 修订依据）

> 本节保留 V1 的问题和评审过程，便于追溯。若本节与第五部分 V2.1 最终方案存在差异，以第五部分为准。

以架构评审视角对 V1 进行自查，发现 8 项问题，按严重程度排序：

### R1.【高】实时订阅通道是"假设"而非"确认的能力"
- **问题**：D7 混合模式的前提是 IoT 平台提供 WebSocket/MQTT 订阅通道，但平台方能力未经确认。若平台只提供 REST API，实时监控只能退化为轮询。
- **修订**：将订阅通道列为**P0 前置确认项**；同时设计**降级路径**——若平台无订阅能力，实时监控页按"绑定拉取周期"轮询展示（并在页面标注数据延迟=拉取周期），架构上把"实时数据源"抽象为可切换的适配器（`RealtimeDataProvider` 接口：订阅实现 / 轮询实现）。

### R2.【高】报警链路语义不清：报警延迟到底多大
- **问题**：V1 报警引擎画在"统计计算"一侧（基于落库聚合数据），意味着报警延迟 ≥ 拉取周期（如 60s）。紧急报警（如急停、超温）不能接受分钟级延迟，但 V1 未区分。
- **修订**：报警分两级——**实时报警**：由订阅通道数据流即时判定（延迟秒级），覆盖紧急/严重等级规则；**统计报警**：基于聚合数据的趋势类规则（如"1小时均值超限"、"OEE 低于阈值"），延迟分钟级可接受。报警规则配置页需标注每条规则的判定数据源。

### R3.【高】绑定唯一性约束缺失
- **问题**：V1 未回答"一台 IoT 设备能否被绑定到多台系统设备"。若允许，同一份指标数据会流入多台系统设备的统计，OEE 等口径重复计算；报警也会重复触发。
- **修订**：**约束：一个 IoT 设备编码全局只能绑定到一台（未停用状态的）系统设备**，绑定校验时由本系统做排他检查。（若业务确有共享场景，如一条产线两套系统设备，留待开放问题 O3。）

### R4.【中】指标元数据同步机制未定义
- **问题**：勾选指标存的是绑定时的快照（名称/单位）。平台侧指标元数据变更（改名、改单位）后，本系统展示与统计口径会出现陈旧或不一致。
- **修订**：增加**每日定时同步任务**：对比平台指标清单与本地快照，元数据变更则更新快照并记录审计日志；**指标编码被平台删除/停用**时不下物理删除，标记为"已失效"，报警规则引用处给出告警提示，需人工处理。

### R5.【中】拉取任务可靠性细节不足
- **问题**：V1 只提"失败重试+回填"，未定义：拉取周期如何调度（分布式下防重复）、平台限流如何应对、回填窗口边界、数据中断判定标准。
- **修订**：
  - 调度：按 `binding_id + binding_item_id + metric_code` 维护独立拉取任务；单机用时间轮/定时任务，分布式用任务分片或 xxl-job，并以任务幂等键和数据库/分布式锁防重复执行
  - 限流：拉取客户端全局限速（令牌桶），超限退避；与平台方确认单账户 QPS 上限（开放问题 O1）
  - 水位与回填：每个任务保存 `source_time_watermark` 和平台分页 `cursor`；拉取窗口使用左闭右开并保留小范围重叠窗口，失败重试 3 次后进入补偿队列；窗口结果通过幂等 Upsert 写入
  - 数据中断判定：区分“无心跳/通信中断”和“设备停机但通信正常”；连续 **N 次（默认 3）**拉取失败或超过 **3×拉取周期**无有效新数据时，来源设备健康状态置为中断，再由绑定健康规则汇总，不直接覆盖配置状态
  - 迟到数据处理：按 `source_time` 归入原始窗口，更新原窗口聚合并增加 `late_count`；超过允许迟到窗口则标记待重算，不能写入下一个窗口

### R6.【中】安全与部署形态缺失
- **问题**：V1 未涉及系统间认证、网络部署、账号权限，真实开发不可缺。
- **修订**：
  - 平台 API 访问：服务账号 + Token（OAuth2 client_credentials 或 AK/SK），Token 定期轮换；所有调用记录审计日志
  - 订阅通道：连接鉴权 + 断线自动重连（指数退避）+ 心跳保活；实时报警事件必须落库，关键实时样本进入 7~30 天短期缓冲；重连后按事件 ID/时间窗口补判或明确记录不可补判
  - 部署：本系统后端与 IoT 平台同内网部署（或经 API 网关），不暴露公网
  - 本系统权限：联网配置为敏感操作，纳入现有权限管理与操作审计（绑定/换绑/解绑/勾选变更全量审计）

### R7.【低】换绑的数据口径细节
- **问题**：V1 有 `binding_version` 但未定义解绑/停用期间的数据与统计口径。
- **修订**：绑定版本采用不可变实例，保存 `effective_from/effective_to`；解绑/停用后聚合、质量、状态和报警数据保留并引用原绑定版本；报表跨版本标注切换点；停用期间规则挂起，重新启用必须显式恢复。

### R8.【低】程序参数比对的 MES 依赖未记录
- **问题**：程序参数比对（客户定制）依赖 MES 下发程序数据，属第三个外部系统依赖，V1 未声明。
- **修订**：在接口依赖清单中单列：MES 程序下发记录查询接口（开放问题 O2：由 MES 推送还是本系统拉取）。

## 第五部分：V2.1 修订方案（开发前基线）

### 5.1 总体架构（修订后）

```
┌──────────────────────────────────────────────────────────────┐
│ 设备管理系统（应用层）                                          │
│                                                               │
│  【配置域】绑定实例（租户/组织范围内，活动 IoT 编码排他）         │
│   系统设备 ⇄ IoT主设备 + N子设备(传感器,带角色)                 │
│   每来源设备勾选指标（指标版本快照 + 每日同步 + 失效标记）        │
│                                                               │
│  【实时域】RealtimeDataProvider（适配器，可降级）               │
│   首选：IoT平台订阅通道(WS/MQTT)  降级：按拉取周期轮询           │
│   → 实时监控展示 + 实时报警事件持久化 + 短期重算缓冲             │
```

### 5.2 V2.1 数据模型（最小可开发模型）

```
device_binding（绑定实例，不覆盖历史版本）
├─ id, tenant_id, org_path, device_id, version
├─ config_status(待配置/已启用/已停用)
├─ health_status(正常/延迟/中断/部分中断)
├─ effective_from, effective_to
└─ created_by, created_at, updated_at

device_binding_item（一个绑定实例下的来源设备）
├─ id, tenant_id, binding_id, iot_device_id, iot_device_code
├─ role(main/sensor), sensor_type, enabled, active
└─ 同一绑定实例内编码唯一；每个实例只能有一个 main

device_binding_metric（来源设备下的勾选指标）
├─ id, binding_item_id, metric_code, metric_version
├─ metric_name, unit, data_type, selected
├─ sync_status(正常/已失效), last_sync_time
└─ 唯一键 = (binding_item_id, metric_code, metric_version)

metric_definition_version（平台指标版本快照）
├─ metric_id, metric_code, metric_version, name, unit, precision, data_type
├─ valid_min, valid_max, effective_from, effective_to
└─ source_schema_version, sync_status；唯一键 = (metric_code, metric_version)

pull_task / pull_task_item（拉取任务与来源指标明细）
├─ task_id, binding_id, binding_item_id, metric_code
├─ window_start, window_end, source_time_watermark, api_cursor
├─ idempotency_key, status, retry_count, error_code, next_retry_at
└─ 来源设备/指标独立记录，支持部分成功、重试和补偿

metric_sample_buffer（短期规范化样本）
├─ device_id, binding_id, binding_version, iot_device_id
├─ metric_code, metric_version, source_time, receive_time
├─ source_value, standard_value, quality_code, idempotency_key, batch_id
└─ 默认保留 7 天，可配置 7~30 天，过期归档或清理

metric_minute_aggregate（分钟聚合事实）
├─ device_id, binding_id, binding_version, iot_device_id
├─ metric_code, metric_version, window_start, window_end
├─ sample_count, valid_count, missing_count, late_count
├─ sum, min, max, avg, first, last, quality_summary
├─ compute_version, is_final, computed_at, revised_at
└─ 唯一键 = (binding_id, iot_device_id, metric_code, metric_version, window_start)

source_device_health / metric_health
├─ binding_item_id, metric_code, health_status
├─ last_source_time, last_receive_time, fail_count
└─ 绑定健康状态由来源设备/指标健康状态汇总，不覆盖配置状态

alarm_rule / alarm_rule_version / alarm_event
├─ alarm_rule 增加 data_source(realtime/aggregated)
├─ 规则版本保存完整条件、恢复、抑制、通知和指标版本快照
└─ 报警事件保存 rule_version_id、binding_version、来源、去重键、恢复和处置记录

mes_program_baseline / mes_program_dispatch / program_compare_record
├─ MES 基线、下发记录、实际运行快照、差异明细分开建模
├─ result: 一致/参数不一致/比对失败/不适用
└─ 处理记录只追加，不允许物理删除

metric_sync_log / binding_audit_log / pull_compensation_queue
├─ 同步差异、绑定勾选变更、失败窗口和人工重放全量留痕
└─ 审计字段含 tenant_id、对象、原因、前后值、结果、IP、终端、trace_id
```

模型约束：

1. 单租户私有化部署对 `device_binding_item.iot_device_id` 建立 `WHERE active = true` 的部分唯一索引；多租户部署使用 `(tenant_id, iot_device_id)` 的 `WHERE active = true` 部分唯一索引。不得用前端校验替代数据库约束；`active` 由绑定实例生效区间和配置状态共同派生或在事务中维护。
2. 绑定换绑采用事务：关闭旧实例、创建新实例、复制或重新选择指标、写入审计，并记录生效时间。
3. 聚合按指标语义计算：数值指标使用统计量，状态指标计算状态时长，计数器计算增量，生产/质量指标使用累计值或事件值；不能统一按均值处理。
4. `source_time` 用于时间窗口归属，`receive_time` 用于延迟和质量统计；存储使用 UTC 或带时区时间，展示统一使用工厂时区 `Asia/Shanghai`。
5. 聚合写入必须使用 Upsert；重复拉取、补偿重放和服务重启不得产生重复事实或重复报警。
6. 小时/日聚合由分钟事实滚动生成并保留计算版本；MTTR/MTBF 必须引用报警、维修和状态事件，不得由数值指标均值推导。

| 3 | 历史数据批量拉取 | 按来源设备/指标/时间窗拉取，支持分页和游标 | IoT 平台 | P0 |
| 4 | 实时数据订阅通道 | 实时监控、实时规则判断、断线恢复 | IoT 平台 | P0 |
| 5 | 设备在线状态/心跳查询 | 来源设备健康和通信状态 | IoT 平台 | P0 |

| 7 | 程序下发记录/基线查询 | 提供 MES 程序基线、版本和下发状态 | MES | P1 |

每个接口在开发前必须形成并签字确认的 OpenAPI/AsyncAPI 契约，至少包含：

1. 鉴权方式、服务账号权限范围、Token 过期和轮换；请求超时、重试、错误码、限流响应和最大批量。
2. 稳定的 `iot_device_id`、`iot_device_code`、`metric_id`、`metric_code`、`event_id` 和 `schema_version`；编码不可复用，变更必须有兼容期。
3. 数据字段：`source_time`、`receive_time`、值、单位、数据类型、质量码、来源端点、批次号和分页游标。
4. 历史接口：时间范围、左闭右开规则、排序稳定性、游标有效期、重复请求语义、补传和最大查询跨度。
5. 订阅接口：协议、消息结构、心跳、断线重连、最后事件 ID、顺序保证、重放能力和权限撤销后的处理。
6. MES 接口：基线版本、实际参数来源、推送或拉取方向、幂等键、版本兼容、分页和失败回调。

```text
WS   /iot/metrics/subscribe

GET  /mes/program-dispatch-records
GET  /iot/devices/{iotDeviceId}/program-snapshot
```

若平台不提供订阅通道，实时页面改为轮询模式并展示实际数据延迟；紧急/重要规则必须改由平台报警事件流提供，或明确降级期间不承诺秒级报警，不能静默降级。

### 5.6 量化验收标准（默认建议值）

以下为开发前的默认验收建议，最终阈值必须写入接口和项目验收协议：

| 类别 | 验收标准 |
|---|---|
| 绑定一致性 | 同一租户下活动 IoT 设备编码不可被两台系统设备占用；并发绑定测试 0 条重复活动绑定；每个绑定实例最多 1 个主设备 |
| 拉取幂等 | 相同任务、窗口和来源指标重复执行 3 次，聚合事实仍只有 1 份；服务在“拉取成功但提交前崩溃”后可安全恢复 |
| 时间语义 | 所有窗口左闭右开；迟到数据按 `source_time` 回写原窗口；源时间与接收时间均可查询；跨班次/跨日测试无边界丢失 |
| 数据质量 | 未配置、不支持、不适用、无数据不得按 0 统计；重复数据不得重复触发报警；缺失、迟到、补传、无效均可追溯 |
| 实时展示 | 订阅模式下大屏刷新周期 5 秒；轮询模式展示实际延迟；连接断开时显示“连接中断”，不得继续伪装为实时正常 |
| 实时报警 | 订阅模式下报警触发到站内事件目标 P95 小于 5 秒；无订阅且无平台报警事件时不得宣称秒级，必须显示降级状态 |
| 统计报警 | 聚合窗口重算后，受影响统计报警在约定时限内完成重算，并保留原计算版本和重算记录 |
| 性能 | 当前状态查询 P95 小于 500ms；报警列表 P95 小于 1s；当天趋势 P95 小于 2s；报表查询 P95 小于 5s |
| 安全审计 | 绑定、换绑、解绑、勾选、补偿重放、规则发布、报警关闭、导出等操作审计覆盖率 100%；越权请求全部拒绝并留痕 |
| 灾备恢复 | 数据库、配置、任务水位和报警事件可恢复；恢复演练达到双方确认的 RPO/RTO，默认建议 RPO 不超过 15 分钟、RTO 不超过 4 小时 |
| MES 比对 | 无基线为“不适用”，读取失败为“比对失败”，不计入参数不一致；差异字段、单位、容差和版本可追溯 |

## 第六部分：开发前决策与签字清单

本节事项不是普通待办。P0 项必须在一期开发前书面确认；P1 项必须在对应阶段启动前确认。未确认时只能做接口模拟和技术验证，不得承诺生产能力。

| # | 决策项 | 当前倾向 | 级别 | 未确认影响 |
|---|--------|----------|------|------------|

| O4 | 平台源时间、接收时间、时钟同步和工厂时区 | `source_time` 归桶、`receive_time` 计延迟、展示 Asia/Shanghai | P0 | 决定窗口、迟到、班次和报表口径 |
| O5 | 是否存在一台 IoT 设备共享给多台系统设备 | 默认活动绑定排他；共享场景须单独设计授权和统计归属 | P0 | 决定唯一约束、报警去重和统计口径 |
| O6 | 紧急/重要报警最大允许延迟和降级行为 | 订阅模式 P95 小于 5 秒；降级必须显式提示 | P0 | 决定报警等级、通知和验收标准 |
| O7 | MES 程序数据推送还是本系统拉取；实际参数来自何处 | 倾向拉取；基线来自 MES，实际参数来源由设备矩阵确认 | P1 | 决定程序比对接口和实时性 |
| O8 | 聚合、短期缓冲和审计数据保留期限及容量预算 | 短期缓冲 7 天；聚合默认 2 年；先测算再定归档 | P1 | 决定数据库、归档和备份方案 |
| O9 | 后端、数据库、队列和部署技术栈 | 技术栈开放，但必须支持契约、幂等、补偿、审计和备份 | P1 | 决定排期、运维和团队能力 |

默认停工条件：O1~O6 任一项没有书面结论，不能进入生产接入和报警开发；只能完成模型、适配器接口、模拟数据和故障测试框架。

## 附：V2.1 修订说明

1. 本方案的核心边界是 **IoT 平台负责设备连接、协议解析、点位配置和原始数据；本系统负责业务绑定、指标选择、聚合读模型、报警事件、报表和审计**。
2. 第四部分保留 V1 问题作为历史追溯；第五部分 V2.1 是当前开发基线，出现冲突时以第五部分为准。
